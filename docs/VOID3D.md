# void3d — 3D Render Layer

The opt-in 3D consumer above Void's GPU bridge, sibling to [void2d](VOID2D.md). It is a port of Heaps `h3d` (`~/projects/heaps`), taken in the order Hibernal needs it.

**Status (2026-09-26):** M1–M13 are built and reviewed (`docs/REVIEWS-3D.md`). The campfire runs through the retained scene, scene lights and the pixel-art preset; M8 adds the CPU-only glTF subset and maps its named node hierarchy into that scene; M9 animates that scene's nodes and swaps baked mesh frames; M10 turns a framebuffer tap into the nearest pickable object; M11 puts CPU particles on a per-frame stream mesh and adds saturation to the look; M12 gives a lit material a saturation of its own, so one object can grey alone; M13 multiplies every light into the material's colour, with Heaps' Lambert for the directional light. The gate is `sh scripts/gate3d.sh`.

## What Hibernal needs

From `~/metascript/hibernal`: `docs/RENDERER-BRIEF.md`, `docs/BRIEF.md` §5.6 (which amends the brief), `docs/ROADMAP.md` V1–V6 and A3/A4/A10/A11.

- **One scene, two surfaces.** The campfire home scene renders in the live wallpaper and in the app, from the same native core (`libhibernal.so`); the HUD is void2d/Neon drawn on top in-app only.
- **The t3ssel8r look.** Render at **360×800** into offscreen targets, integer-scale **3×** to 1080×2400 with nearest sampling. Passes: color + depth, normals, outline from depth + normal edges, palette quantization through a LUT, blit.
- **Pixel-perfect camera.** Orthographic, fixed yaw/pitch, snapped to the low-res texel grid; the sub-pixel remainder is applied as an offset in the blit. Without it the image shimmers — the brief calls it the single most important item.
- **Content.** Low-poly meshes, ≤500 tris per pet, ≤200 per prop, position + normal + vertex color, no textures on the pet, loaded from a glTF subset exported by a Blender generator.
- **Lighting.** One directional light plus one campfire point light, a toon ramp in the color shader, fire flicker stepped at 10–12 fps.
- **Animation.** Vertex-baked keyframes stepped at 12 fps. No skinning.
- **Interaction.** Tap the pet (pick), tap-and-hold (the host deep-links).
- **State-driven looks.** Palette swap for day/night, Winter and a Fading pet; fire size from hearts; harvest objects appear in the scene; snow. The mapping from game state lives in Hibernal, void3d only has to make each of these a parameter.
- **Wallpaper constraints (V6).** 30 fps target, ~10 fps or on demand when idle, stop when invisible, no allocation in the frame loop, every GPU resource rebuildable after context loss, a reduced-fidelity preview path.

## Porting rules

sokol replaces `h3d/impl` (drivers) and `hxsl` (shader compiler), so the port covers the layers above them.

Kept from Heaps: row-vector matrices and `local * parent` world transforms; the `posChanged` lazy sync of `h3d.scene.Object`; Material → Pass → render state; a Renderer that owns an ordered list of passes; depth in `[0, 1]`.

Changed on purpose:

- **Y up, right-handed** (Heaps: Z up, left-handed). glTF, the Blender exporter and the spike are Y up.
- **Fixed sokol-shdc programs instead of hxsl shader lists.** A Material names one program and carries its uniform values. Composable fragments stay deferred (`docs/SHADER.md` Tier 3).
- **The renderer consumes a draw list, not the scene tree.** Heaps' `emitRec` fills per-pass object lists during the walk; here the scene flattens to `Vec<DrawItem>` only when its structure changes, and each frame only rewrites world matrices. The renderer works (and is tested) with no scene at all.

Not ported: `hxsl`, `h3d/impl`, PBR (`scene/pbr`, `shader/pbr`), shadow maps, skinning (`anim/Skin`, `scene/Skin`), `World`/`HierarchicalWorld`, `GpuParticles`, `MeshBatch`/`Batcher` beyond instanced billboards, `RenderGraph`, `CameraController`.

## Data types

Storage is a plain retained tree: a Hibernal scene is tens of objects, and at that size layout costs nothing measurable. What is taken from [SCENE-SCALE.md](SCENE-SCALE.md) is how the **types** are cut, so that the tree could be moved to columns later without changing callers:

- **Per-node state is value structs grouped by the pass that reads it.** `Transform3D { position: Vec3; rotation: Quat; scale: Vec3 }` is one field; `world: Mat4` is another. An `h3d.scene.Object` allocates four times (itself, `absPos`, `qRot`, `children`); here only the node and its `children` array allocate.
- **Small node, kind data in side tables.** `Object3D` carries `kind`, `flags` (visible, posChanged, culled as bits), `local`, `world`, `children` and a `payload: int32` indexing the scene's `meshes: Vec<MeshInstance>` or `lights: Vec<Light>`. The opposite of `Node2D`'s 71 fields.
- **Assets are CPU data plus GPU handles.** `MeshData` keeps its vertex/index arrays; GPU buffers are `uint32` handles created from them and can be recreated from them after context loss. The same holds for what the library itself owns: the palette LUT, the render targets, the samplers and the pipelines. Textures and buffers a caller makes (the campfire's billboard atlases and instance buffers) are the caller's to rebuild; the example's `forceRebuild` is that work.
- **Frame state is preallocated.** Uniform blocks are `Vec<float32>` sized once; the draw list is rebuilt only on structural change; nothing in `frame` allocates.
- **Handles into scene tables are indices**, not references, so a draw item or a pick result is a plain value.

**The scope of every pixel claim in this document.** Every byte-identity claim here is D3D11 swapchain readback on one Windows box. Nothing has been compared byte for byte on any other backend, and GLES3 — the backend Hibernal actually ships on, and the one most likely to contract floating-point arithmetic differently — has no byte-level numbers at all.

**What did happen, before M7 touches a shader: the GLES3 path ran.** Through M3, M4, M5 and M6 the `android` stage built the arm64 `.so` and never executed it, so nothing was known about whether the port even starts on GLES3. It does. `libVoidAndroid.so` loads, `libGLESv2_emulation.so` opens, the renderer attaches at 320x640 and holds ~30 fps, and the frame it draws is the campfire — ground, boxes lit by the fire with its falloff, grass billboards, the flame, the night palette — at 2830 unique colours against the D3D11 frame's 3041. The M6 model-matrix path is in that image, so the whole scene-to-shader chain works on GLES3 and not only on D3D11. `tests/device/gles3Campfire.png` is the frame, committed, with its recipe.

**What that run does not establish, stated so nobody reads it as more than it is.** It was the **Android emulator**, not a device: `ro.hardware.egl` is `emulation`, the GL is `libGLESv2_emulation.so` translating to the host's driver, and the CPU is x86_64 running the arm64 library under binary translation. So it says nothing about an Adreno or Mali driver, nothing about mobile float behaviour, and nothing about contraction on real hardware — the FMA result above stays a D3D11 result. Nor is it a pixel comparison: at 320x640 against 1280x720 there is no baseline to compare with, and the numbers above are colour statistics and a human looking at the image. The gap has gone from "never executed" to "executed, on an emulator, unverified against any baseline", which is narrower and is not closed. Tracked as `gles3-emulator-only` in [tests/PENDING3D.md](../tests/PENDING3D.md).

**Measured before M6 was written: placing the campfire by matrix moves no pixel.** The worry was concrete. `addBox` bakes each corner with `toWorld`, computing `base.x + local.x*yawCos + (local.y*tiltSin + local.z*tiltCos)*yawSin`; the same placement as a matrix computes `local.x*yawCos + local.y*(tiltSin*yawSin) + local.z*(tiltCos*yawSin) + base.x`, moving the translation from the front of the sum to the back and turning one product of a sum into a sum of two products. float32 addition is not associative, so the two are equal in real arithmetic and not in this one: `out/tmp/worldProbe` runs both over the leaning log from the pinned test and **4 of its 5 corners differ, by 1 or 2 ulps** — `0.12782013416290283` baked against `0.12782010436058044` by matrix.

That is a claim about vertex floats, and byte-identity is a claim about the image. They are different claims, so the second was measured rather than inferred from the first. `toWorld` was routed through a `Mat4` and the whole gate re-run: **all six capture configurations stayed byte-identical**, tests included. The null result is a real one and not a stale binary — the control, the same matrix with `+0.01` on its x translation, fails every configuration loudly: AE **1820, 1848, 1748, 1836** across the four palette-off frames at PAE 59110, and the arm64 `.so` changes size on both runs. A ~3e-8 world-space perturbation does not carry a triangle edge across D3D11's 1/256-pixel coverage boundary at 360x800, and what survives that is then quantized through the palette LUT.

**So there is no conflict and no baked fallback.** M6 puts the campfire's stones and logs on real nodes with real model matrices, and `DrawItem.world` is exercised by the actual scene rather than by one object built to exercise it. One caveat is left open rather than assumed away: this measurement multiplied on the CPU, and the shipped path multiplies in the vertex shader, where the GPU may contract `a*b + c` to an FMA and land on a different last bit. The same six configurations are what answer that, and they run before the milestone closes.

Possible feedback into void2d (not part of this plan): if the small-node + side-table split works here, `Node2D` is the obvious next candidate.

### M2 as built

- **Bridge.** `gpu3d.c` turns flat arrays into `sg_*_desc` and nothing else: a program table (`Program` → `*_shader_desc(sg_query_backend())`), three vertex layouts (`Lit`, `Billboard` with an instance buffer in slot 1, `Fullscreen`), and ordinal → sokol tables for every enum, each with a `_Static_assert` on its length against the MetaScript enum (order is still kept by hand). Descriptor layouts are `static const int32_t` in `gpu3d.h`, the one form of constant msc imports from a header. Front faces are CCW.
- **MetaScript side.** `gpu3d.ms` (enums, uniform slots, thin wrappers), `pass.ms` (`RenderState`: culling, depth, blend, colorMask, `setBlendMode`; `bits()`/`fromBits` like `Pass.bits`/`loadBits`), `target.ms` (`RenderTarget` with attachment + optional texture view, `Sampler`, attachments with load/clear, `TargetLayout`, `beginPass`), `pipelineCache.ms` (`PipelineKey`, 64 bits = layout, program, target formats, state bits, decodable back into its parts; lazy `pipelineFor`), `material.ms` (program + render state + textures + uniform block), `draw.ms` (`GpuMesh`, `DrawItem`, `DrawContext` with a uniform pool sized once, `drawItems`).
- **Diagnostics.** `toString` on `RenderState`, `TargetLayout` and `PipelineKey` prints one line (`program=Billboard layout=Billboard colors=Rgba8,Rgba8 depth=Depth sampleCount=1 culling=None …`), the role of Heaps' `CachedPipeline.getFields`: when a cache miss is unexpected, print both keys. It allocates, so it stays out of the frame loop.
- **Rebuild after context loss.** Targets keep size and format, samplers keep their settings, the pipeline cache keeps its keys (`forgetPipelines` drops handles, the next `pipelineFor` rebuilds). Meshes and data textures are uploaded from buffers the spike does not keep; their CPU copies come with M5.
- **Not yet used:** `DrawItem.world` (the programs take world-space vertices; the model matrix comes with M6), index buffers (M5 adds the pipeline index type), `Face.Both`, stencil, per-target color masks.
- **Acceptance.** The campfire's setup and frame order were in `src/examples/campfirePasses.ms` (replaced by the renderer in M3); `pass3d.c/.h` are deleted. A D3D11 readback of the resolved swapchain at 1280×720, frames 1, 6, 11 and 16 (different flicker and flame frames), is byte-identical before and after. The cache creates 4 pipelines over the run (grass and flame share one). The arm64 Android `.so` builds.

### M3 as built

- **Core and preset, as in Heaps.** Heaps splits its renderer into a base that draws nothing (`h3d.scene.Renderer`: pass lists, sorting, targets, `effects`), presets built on it (`fwd.Renderer`, `pbr.Renderer` with `RenderProps`; a game subclasses one, as `samples/Sao.hx` does for SSAO) and building blocks (`h3d.pass.*`). void3d keeps the same three layers, so Void stays a pure rendering library and no game is favored:
  - **Core** (`renderer.ms`, `scene/Renderer`). `Renderer` owns the pass lists, the camera and light uniform blocks, the screen triangle and the GPU context bookkeeping. A preset calls `beginFrame` (adopts a new context, uploads camera and lights, fills and sorts the pass lists; returns true when the preset must rebuild its own GPU objects), `drawPassLists` (Heaps' default, alpha, additive), `drawScreen` (ScreenFx over the current pass) and `endFrame`, in its own order. It takes a `Span<DrawItem>` and the camera block, never a scene. `markChanged` / `needsFrame` live here.
  - **Pixel-art preset** (`pixelArtRenderer.ms`, in the role of `scene/fwd/Renderer`). `PixelArtRenderer` wraps the core and owns the four low-res targets (color, normal, depth, post), the sampler, the palette LUT and the post/blit materials. `renderFrame(renderer, context, items, camera, lights, view)` runs the stages of `planStages(settings)`: `Scene` (the core's pass lists into MRT color + normal with a depth attachment), `Post`, `Blit`. `PixelArtSettings` and `PixelArtLook` (outline, fog, background) and the palette are all the caller's; Hibernal's numbers are only the defaults of `PixelArtSettings.full()`. `PixelArtRenderer.create` reserves `PIXEL_ART_UNIFORM_LENGTH` floats (core blocks included) and makes no GPU object; the first frame does.
  - **Building blocks**: `passList.ms`, `screenFx.ms`, `blit.ms`, `palette.ms` below, usable by any other preset.
- **Why composition, and where polymorphism goes.** Nothing calls "some renderer" yet: Hibernal and the campfire use `PixelArtRenderer` directly, so there is no polymorphic call site and the preset simply calls the core's functions (static calls, no allocation, value types throughout). Heaps' `process()` → abstract `render()` is the only template method in its base; here `beginFrame`/`endFrame` are its preamble and epilogue and the preset's `renderFrame` is `render()`. The static form of that template method (a generic `runFrame<P>(ref core, ref preset: P)` calling an exported extension on `P`) does not build on 0.2.53 (see "Waiting on a newer msc"). Polymorphism arrives with `h3d.impl.RendererFX` (M11: desaturation for a Fading pet, later bloom): effects plugged into the steps of any preset, a heterogeneous list at runtime, so an `interface` with function-typed fields as Neon's `Host` seam does, or a discriminated union if void3d keeps the set closed. Decided when M11 lands.
- **Pass lists** (`passList.ms`, from `pass/PassList`). `Material.phase` (`Opaque`, `Alpha`, `Additive`: fwd.Renderer's "default", "alpha", "additive") picks the list; `collect` keeps item order, `sortBackToFront` is `depthSort` (stable insertion sort on clip z of the item's world translation). Index storage grows only with the item count. Sorting has nothing to do until M6 fills `DrawItem.world`.
- **Screen passes** (`screenFx.ms`, from `pass/ScreenFx`, `Copy`, `Outline`). A screen effect is an ordinary `Material` on the `Fullscreen` layout drawn as one item over one triangle, so it goes through the pipeline cache like the scene. Materials now carry four textures and two samplers.
- **Post pass**, one program (`postFs`): outline from depth + normal edges, depth fog, then palette quantization, which reads only the outlined pixel, so one pass is enough. `features` switches outline, palette and the depth source per frame through uniforms; no switch makes a new pipeline.
- **Palette LUT** (`palette.ms`). `levels`³ cells (16 by default, up to 32) stored `levels²` × `levels`, cell (r, g, b) at x = r + b·levels, y = g; the post shader rounds each channel to a level and fetches. `fill` maps every cell to the nearest palette color (0xRRGGBB, weighted squared RGB 2:4:3, first wins a tie) into CPU pixels; `upload` sends them to one dynamic image, so a palette swap rewrites pixels and never touches a pipeline. An unfilled LUT is the identity at its level count. `setPalette` fills; the `palette` setting turns it on.
- **Blit** (`blit.ms`). `lowResView(framebuffer, shortSide, divisor, margin)`: scale = max(1, short side / 360) × divisor, the target covers the framebuffer rounded up to whole texels plus `margin` on every side, the overhang is split between both sides. `withRemainder(x, y, originTopLeft)` adds the camera's snap remainder (true minus snapped position, low-res texels along the camera's right and up, each in [0, 1)) as `remainder × scale` framebuffer pixels; up is −y on D3D11/Metal and +y on GL (`gpu3d originTopLeft`). M4 supplies the remainder and sets `margin: 1`, and adds `texelAt` / `framebufferAt` so the shader's `texel = floor((fragment + offset) / scale)` is written once and the camera reads it back the other way. The blit writes alpha 1.
- **Preview** (`PixelArtSettings.preview()`, RENDERER-BRIEF §4.1): half resolution (180×400 at 6× on 1080×2400) and no outline, same palette and pipelines. `postPass: false` goes further: the blit reads the scene color directly, with no outline, fog or palette. Frame rate stays the host's.
- **Nothing changed** (V6). The core's `needsFrame()` is true after `markChanged` (which the scene calls until M6 tracks its own dirty state) or on a new GPU context; the preset's `needsFrame(view)` adds any setting, look or palette change and a new view (size or sub-pixel offset). `endFrame` clears it.
- **Acceptance.** With the palette off, a D3D11 readback of the campfire (1280×720, frames 1, 6, 11, 16) is byte-identical to M2 and to the pre-M2 images. With the sample night palette (`CAMPFIRE_PALETTE`, 21 colors) the frames are quantized as expected and stable across runs. Preview, `postPass: false` and `DepthSource.DepthTexture` were each captured and render correctly. The arm64 Android `.so` builds. `campfirePasses.ms` is deleted; the campfire's materials and meshes moved into `campfireScene.ms`, which calls the renderer (`configureCampfire(settings, palette)` selects a configuration for the checks).
- **On the new sokol pin.** After merging into `main`, which moved sokol to `2e75443d`, the gate ran again on that pin (C objects evicted from both msc caches first): tests pass, and all five campfire configurations read back byte-identical to the `6c3fa5ac` images; the arm64 `.so` builds.
- **HLSL note.** fxc warns `X4000: use of potentially uninitialized variable (depthAt)` when it inlines the post shader's `depthAt` into the edge loop; the generated HLSL initializes the variable on every path and the output is unaffected.

### M4 as built

- **Two structs, request and result.** `OrthoCamera` is what the caller wants: a `target`, a fixed `yaw`/`pitch`, `worldPerTexel` (world units one low-res texel covers), `nearPlane`/`farPlane` and a `snap` flag. `resolve(texelWidth, texelHeight)` returns a `CameraView`: the snapped eye and its basis, the `viewProj` the scene programs read, and the remainder the snap left over. Keeping them apart is the whole point — "where the camera wants to be" moves smoothly, "where it renders from" only ever sits on a texel.
- **No eye distance.** An orthographic camera has no position along its view direction: sliding it there moves the clip planes and nothing else. So the target *is* the eye, and `nearPlane`/`farPlane` say what is visible in front of and behind it (the campfire's spike camera, at distance 50 with a depth range of 100, is `nearPlane: -50, farPlane: 50`). Dropping the distance also removed a ~1.5e-7 phantom translation in the matrix, which was enough to flip 64 framebuffer pixels of the acceptance image.
- **The port.** `basisOf` is Heaps' lookAt basis with world up at +Y, written as trigonometry so the axes are unit-length with no normalize; `makeCameraMatrix` is the transposed lookAt; `orthoBounds` + `projectionMatrix` are `makeFrustumMatrix`'s `orthoBounds` branch; `viewProj = cameraMatrix * projection` with math3d's row-vector product. Heaps' `rightHanded` negates the camera matrix's third column and negates the projection's z back; both are folded away, so the third column is the view direction and z maps `[near, far]` onto `[0, 1]`. The result is Heaps with `rightHanded = true`.
- **The snap** (RENDERER-BRIEF §3.3). The grid is the camera's own: the eye's components along `right` and `up` are measured in texels and floored, and the component along `forward` is left alone. `remainder = true − snapped`, in texels, in `[0, 1)` by construction — a float minus its own floor is exact, in both directions. The caller passes it to `viewFor`, the blit shifts the image back by `remainder × scale`, and the two cancel: `cameraCheck.ms` projects a world point through the snapped view with the shifted blit and through the unsnapped view with the plain blit, in both row orders, and gets the same framebuffer pixel. That test is what pins M3's `withRemainder` sign convention to M4's definition of the remainder.
- **`project` and `rayFromScreen` speak framebuffer pixels**, not texels, because a tap arrives in framebuffer pixels. Both go through the blit's own mapping (`blit.ms` `texelAt` / `framebufferAt`, the shader's formula minus its floor), so the screen mapping is stated once and never restated against the shader. `rayFromScreen` inverts the viewProj and takes the points at z 0 and 1, as Heaps does; orthographic, so the direction is the view direction for every pixel, and reading it off the matrix anyway is what checks the matrix. `Ray` lives here until M10 gives it a module with the intersection tests.
- **`margin: 1` is the caller's, not `full()`'s.** A remainder shifts the image by up to a texel, so a snapping camera needs one texel of margin or the blit clamps and smears the outermost row. It is still not the default of `PixelArtSettings.full()`: the margin changes the low-res target size and therefore every pixel of the image, so making it default would silently change the output of a caller with a static camera, or one that snaps in its own way. `full()` stays the plain full-fidelity preset and a snapping caller writes `{ ...PixelArtSettings.full(), margin: 1 }`, which the camera picks up on its own — the ortho extents come from the target size, so the extra texel is rendered rather than invented (tested).
- **No module-level buffer.** The spike's `camera.ms` owned a `vertexParams: Vec<float32>` that every caller wrote through; `writeCameraBlock(view, out)` writes into the caller's span instead, and `CAMERA_BLOCK_LENGTH` is asserted against gpu3d's `VERTEX_UNIFORM_LENGTH` in the tests. Nothing in the camera allocates or touches the GPU, so a lost context costs it nothing and all twelve tests run headless.
- **The campfire** gets `configureCampfireCamera(snap, panPerFrame)` and builds its camera from `worldPerTexel`. The low-res size does not depend on the camera, so the frame makes the view twice: once with a zero remainder to learn the texel grid, once with the remainder the snap left.
- **Acceptance, no regression.** With `snap: false` and `margin: 0` all five capture configurations of M2 and M3 read back **byte-identical**: the palette-off frames 1, 6, 11, 16 against the pre-M2 `before_*`, the palette frames against `m3palette_*`, and preview, `postPass: false` and `DepthTexture` against their M3 images. Three of the 24 camera-block floats differ from the spike's by one ulp — the spike divided where a matrix product multiplies by a reciprocal — and no pixel moves. The arm64 Android `.so` builds.
- **Acceptance, the snap measured.** The campfire pans 0.3 texel per frame along the camera's right axis for 30 frames, captured with the snap on and off (`out/tmp/capture/campfire{Pan,Shimmer}[Texel].ms`, analysed by `out/tmp/pan/analyze.py`). The campfire re-rolls its flicker every 4 frames, so frames within one group have identical scene content; for each such pair the script searches the integer translation that lines the two up and reports the residual. **Snap on:** every pair is a translation, residual 0 to 176 pixels of 921600 (≤0.02%), and those are isolated single texels on geometry edges — 107 of them spread over 87 rows, at most 5 in any one row. **Snap off:** no pair is a translation at any offset; the best residual is 98k to 364k pixels (11–39%), which is the silhouette re-rasterizing, i.e. the shimmer. The same run at one pixel per texel (`lowResShortSide: 720`, where the swapchain *is* the low-res image) shows the same split: 19–107 pixels against 148k–196k. The measured shift sequence is the other half of the story: with the snap on the image advances by +1, +1, +2 framebuffer pixels over three frames — sub-texel motion at 2× — while with it off it only ever moves in whole texels, +0, +2, +2.
- **What the snap does not buy.** A translated matrix is not bit-identical to the original one, so a hundred-odd texels on geometry edges still flip between frames. That is 1500× smaller than the shimmer it replaces, and it is the same 8-bit knife edge the outline thresholds already sit on (Open questions), not a second mechanism.

### M5 as built

- **Two files, both pure CPU.** `bounds.ms` is `h3d.col.Bounds` and `meshData.ms` is the `h3d.prim.Polygon` role. Neither touches the driver, so both are covered headlessly (47 tests with the review's additions) and both are what a lost GPU context is rebuilt *from*. `src/void3d/mesh.ms` is deleted.
- **`Bounds` is a value struct, not a mutable object.** Heaps' `Bounds` is a class that mutates in place and hands out `clone()`s; here it is two `Vec3` (24 bytes), so it can be a field of `MeshData`, be returned, and be built in a loop without allocating. Empty is Heaps' empty — min at +1e20, max at −1e20 — so the first point lands on both sides and an empty box answers false to every containment test. `contains` keeps Heaps' min-inclusive, max-exclusive rule; `collide` keeps Heaps' touching-counts rule; `transformed` is `transform(m)` over the eight corners, and an empty box stays empty rather than collapsing onto the matrix translation. The builders that accumulate (`addPos`, `addPoint`, `addBounds`) take `ref`. **Heaps' `add` had to become `addBounds`**: a `ref`-receiver free function is not an extension, so it does not arrive with the module import and it competes in the ordinary overload set, where std's `Set.add` / `HashSet.add` already live (card `~/metascript/.inbox/compiler/2026-09-20-ref-receiver-not-an-extension.md`, which lists every site that gets Heaps' names back when a `ref` receiver lands).
- **Three places `Bounds` deliberately does not do what Heaps does**, all of them about emptiness. Heaps' `transform` tests empty with an **AND** over the three axes (`Bounds.hx:159`), so a box empty on one axis only is transformed anyway; `isEmpty` here is an **OR**, so `transformed` leaves it alone. Heaps' `add` merges axis by axis with no emptiness test at all (`Bounds.hx:205`), so adding an empty box drags the result out to ±1e20; `addBounds` returns early instead. And Heaps' `getSize` / `dimension` on an empty box answer −2e20 per axis (`Bounds.hx:329`, `:389`) where `size()` and `dimension()` answer zero. All three are the conservative reading and all three are tested; `boundingSphereRadius` diverges for a fourth reason — Heaps squares the edges directly because its floats are 64-bit, and `Bounds.all()` spans 2e20 per axis, whose square is infinity in float32, so the extent is scaled by its longest edge first.
- **Not ported from `Bounds`**, and none of it needed before M10: `rayIntersection`, `inFrustum`, `inFrustumDetails`, `intersection`, `transform3x3`, `addTransform`, `getVolume`, `toSphere`, `getBoundingRadius`, `distanceTo`, `scalePivot`, `scaleCenter`, `load`, `setMin`, `setMax`, `containsSphere`, `addSphere`, `addSpherePos`, and the `Sphere` / `Plane` / `Collider` types they need. `intersection` and `transform3x3` are the two M10 will actually want.
- **`MeshData` interleaves where Heaps parallelises.** `Polygon` keeps `points`, `normals`, `uvs` and `colors` as four arrays and interleaves them in `getCPUBuffer` at upload time; here one `Vec<float32>` in the `Lit` layout (position 3, normal 3, rgba 4) *is* the storage. There is one vertex layout and it is the one the fixed sokol-shdc programs and Hibernal's content have, so the four-array form would buy only a format switch that does not exist. No UVs and no tangents: the `Lit` program has no texture, and `addUVs` / `addTangents` are not ported.
- **Bounds are maintained, not computed on demand.** Heaps' `Polygon.getBounds()` walks the points each time it is asked. Here the builders are the only writers, so every `addVertex` grows `data.bounds` and it cannot go stale. `recomputeBounds` (Heaps' `getBounds`) stays for the one caller that will edit `vertices` itself: a vertex-baked animation frame in M9. A test asserts the two agree on a turned and tilted box.
- **uint16 indices, and the builders are indexed.** `addQuad` writes four vertices and six indices where the spike wrote six vertices — which is what an indexed mesh with per-face normals wants, since a corner cannot be shared across faces anyway. `addBox` is `Cube`'s role (five quads: top and four sides, no underside, as the spike had it) and `addPlane` is `Plane2D`'s, turned into the ground plane a Y-up world wants. **The arithmetic is the spike's, moved rather than rewritten** — the same `sinf`/`cosf` from `src/math/mat4.ms`, the same term order in `toWorld` — so the campfire's vertex floats are bit-identical and the byte-identity below proves the new plumbing rather than new math. 65536 vertices is the cap (`MAX_MESH_VERTICES`); Hibernal's budget is 500 triangles per pet, so a mesh that does not fit is a content constraint, not a reason to widen the format.
- **Index buffers through the bridge.** `gpu3dMakeIndexBuffer(const uint16_t *, int64_t)`, declared in `gpu3d.ms` as an `extern` taking `Span<uint16>` so it lowers to the pointer/length pair rather than the `Borrow` copy (Compiler notes). sokol bakes the index type into the pipeline, so `IndexType { None, Uint16 }` became a descriptor field (`GPU3D_PIPELINE_INDEX_TYPE`, descriptor length 18 → 19) with its own ordinal table and `_Static_assert`, and a bit of the pipeline key.
- **The pipeline key was exactly full, and the indexed flag took the bit next to the vertex layout.** The 64 bits were vertex layout (4) + program (4) + target formats (24) + `RenderState.bits` (32). `VertexLayout` has three members, so the layout field is now three bits and the fourth is `indexed`; `LAYOUT_LIMIT` is the constant that says so and a test holds all three layouts against it. The alternative — a second key word — costs a wider struct and a two-word compare on every cache lookup, for one bit. **The campfire still creates exactly 4 pipelines** (measured), because the `Lit` program is now always drawn indexed: the indexed variant replaced the non-indexed one rather than joining it.
- **CPU data lives in the `DrawContext`, beside the GPU handles.** `meshes` and `meshData` are one index space: `meshData[i]` is the geometry `meshes[i]` was uploaded from, or an empty `MeshData` for a mesh whose buffers its owner keeps (the screen triangle, billboard corners, billboard instances). `addMeshData` takes a copy — a `MeshData` owns two `Vec` and a `Vec` assignment copies — uploads it, and returns the index both tables now share; `addMesh` is unchanged for the other kind and pushes an empty entry to keep the tables parallel. `meshFor(data, vertexBuffer, indexBuffer, generation)` is the pure half of an upload, so what the counts and the indexed flag are is decided by arithmetic a test can check with no GPU.
- **Rebuild is generation-guarded, which is what keeps it from being a leak.** `GpuMesh.generation` is the GPU context its handles belong to. The core's `beginFrame` calls `rebuildMeshes` on the frame that sees a new `contextGeneration`, and that re-uploads only meshes whose handles are older — `isStale(data, generation)` is CPU data plus an older generation. Without the guard the very first frame would re-upload everything: `renderer.generation` starts at 0 and `contextGeneration()` is 1 from the first frame, so frame 1 is always "fresh", and every mesh would have been uploaded twice with the first pair of buffers dropped and never destroyed. Handles are dropped rather than destroyed on a real loss, because after `sg_setup` an old id can already name a new object (Android lifecycle).
- **The campfire is one indexed `MeshData`.** Measured at frame 17: 26 stones, 3 logs and the ground plane give **584 vertices and 876 indices** (292 triangles) where the spike had 876 vertices and no indices — the same 292 triangles, 33% fewer vertices, 35 040 bytes of vertex data down to 23 360 + 1 752. Its bounds are (−40, −0.060, −40) to (40, 4.60, 40); the y minimum is below zero because one log leans past the ground plane. 7 meshes in the context (lit geometry, grass, four flame frames, the screen triangle), of which **1 is rebuildable** — and that one is the whole of the campfire's lit geometry.
- **Acceptance, byte-identical.** All five capture configurations read back byte-identical to their baselines with the campfire rebuilt on `MeshData`, indexed, and drawn through a new pipeline: frames 1, 6, 11 and 16 of palette-off against the pre-M2 `before_*`, palette-on against `m3palette_*`, and preview / `postPass: false` / `DepthTexture` against `m3preview_*`, `m3direct_*`, `m3depth_*`. **484 tests**, 437 before M5. A sixth configuration re-uploads the geometry mid-run and lands on the same `before_*` images. The arm64 Android `.so` builds.
- **On those three baselines.** `m3preview_*`, `m3direct_*` and `m3depth_*` did not exist in this worktree — the M4 worktree's copies were never carried over, and `out/tmp` is gitignored — so the gate was skipping three of its five configurations. They were **taken fresh at `16c6546`**, the M4 tip, before a line of M5 was written, with `GATE_ADOPT=1`. They are pre-M5 images of M4 code, which is exactly what M5 has to preserve, and their content was checked against what M3 claims: 21 distinct colours for preview and for palette-on (the 21-colour sample palette), 933 for `postPass: false` (no palette, no outline), and 3421 for `DepthTexture` against 3056 for the plain frame, which is the ~15% depth-source difference M3 measured. No baseline that existed was replaced. **Say plainly what that check is and is not**: adopting an image and then comparing against it is circular by construction, so it establishes that these three are *plausible* M4 images, not that they are the M4 images. The non-circular evidence — the M4 worktree's own copies — no longer exists. The two baselines that carry the real weight, `before_*` and `m3palette_*`, are the originals and were not touched.
- **The gate** (`scripts/gate3d.sh`, written and committed first, as the M5 brief required). Four stages, one PASS/FAIL/SKIP line each: **prepare** regenerates `out/tmp/campfireScene.ms` and all five capture entries from `src/`, and checks the patch by inverting it — the inverse `sed` has to reproduce the example byte for byte, which is what says nothing but the imports and the one `as int32` was rewritten; **tests**; **capture** builds, runs and `cmp`s all four frames of each of the five configurations, printing `magick compare` AE and PAE when one differs; **android**. A missing baseline is a loud SKIP and never a pass, and `GATE_ADOPT=1` is the only way one gets written. The gate exits 0 on a SKIP and says so in its last line (`GATE GREEN with N skipped stage(s)`), so "green" and "green with skips" are different sentences — M5's numbers below are from a run with **zero** skips. A sixth stage checks the twenty baselines against `docs/baselines3d.sha256`, which is committed: the images are gitignored, so without the manifest nobody could tell six months from now whether the files they hold are the ones a byte-identity claim was made against. The capture entries are generated rather than kept by hand, because an entry that lives only in gitignored `out/tmp` is one bad night from being lost or silently edited. The failure mode that would otherwise be silent is the object cache: `msc build` answers "Up to date" when only a header a compiled `.c` includes has changed, so the gate hashes `shader3d.glsl.h` and `gpu3d.h` together and, when that hash moves, evicts this checkout's build cache and the one global object that mentions `gpu3d`. It did exactly that on the M5 bridge change, and the images still matched. Green end to end in 17.5 s.

**Still missing after M5.** The campfire example's own GPU resources are still not rebuilt after a context loss: the billboard corner buffer, the grass instance buffer, the four flame instance buffers and the two generated textures (tuft, flame). They are the example's data rather than the renderer's, and regenerating them would re-roll the shared `nextRandom()` state and change the image, so closing it needs either kept pixels or a reset seed; M6 rewrites this example onto an `Object3D` tree and is where that belongs. Nothing in the rebuild path has run **on a device**: `voidEmbedLoseContext` is Android-only and on D3D11 `contextGeneration()` is the constant 1, so a real context loss has never happened here. The re-upload branch itself is no longer untried, though — the sixth capture configuration (`campfireRebuildCapture`) marks every mesh stale at frame 3 and lets `rebuildMeshes` run: it re-uploads exactly the one mesh that carries CPU data onto new buffer ids, leaves the five that do not alone, and frames 6, 11 and 16 captured after it are byte-identical to `before_*`. The guard against the opposite mistake is measured too: the lit mesh's buffer ids are unchanged from `addMeshData` through frame 3, so the always-fresh first frame does not upload it a second time.

**Two things the rebuild still does not do.** `uploadMesh` never destroys the buffers it replaces. That is right for a real context loss, where they are already gone, and nothing leaks today because no other path re-uploads a live mesh — but `recomputeBounds` exists for exactly such a path in M9, a vertex-baked frame swapping positions under a mesh that keeps its indices, and that would leak two buffers per swap. And `addMeshData` does not `markChanged` the renderer, so a mesh added after the first frame can be invisible for one frame to a host on the on-demand pacing (V6).

M3 and M6 end with the campfire running on D3D11 here and as a `.so` for Android. Every milestone adds headless tests to `src/test/` for whatever does not need a GPU (math, camera snap, bounds, sync, glTF parsing, animation stepping, picking).

### The Heaps oracle

Every claim in this document about what Heaps does used to rest on somebody having read the file — "Heaps' `getSize` on an empty box answers −2e20 per axis (`Bounds.hx:329`)" was a citation, not a measurement, and this is a document whose whole posture is that numbers are measured. `scripts/oracle.sh` closes that: cases are data rows with no expected answer, `regen` replays them through **real Heaps at `2b84cc2`** compiled to JS and run on node, and the answers are committed as `tests/oracle/bounds3d.snapshot`. An ordinary gate run checks the port against that snapshot and needs no Haxe. The harness is deliberately not h3d-specific — everything library-specific lives in the case file, because void2d will want the same thing against h2d.

A case may declare `diverges=<PENDING3D row>`, and those are checked **in both directions**: a declared divergence that starts agreeing fails the run and names the row to reconcile, exactly as a PENDING3D sentinel does. Verified by making `size()` answer Heaps' −2e20 and watching two cases graduate.

**Its first two runs corrected this document, which is the point of building it.** `bounds-sphere-rescale` was written up as a divergence; the answers agree to 4.6e-9 relative, so it is a divergence in method forced by float32 and not a difference in behaviour. And `bounds-transformed-or` was described as applying to a box "empty on one axis" — but a *flat* axis (min == max) is empty under neither Heaps' rule nor this port's, so the real divergence needs a genuinely negative extent: with one, Heaps answers `10 -1 0` where this port answers `0 0 0`. Thirty-three cases over two files now: thirty agree, three diverge as declared.

**The scene tree is measured too, and it is where the M6 claims were.** `tests/oracle/scene3d.cases` is sixteen cases against a bare `h3d.scene.Object` tree, and all sixteen agree. They cover what M6 asserted only against itself: that `world` is `local * parent` and not the reverse (a quarter turn about Y on the parent takes a child at +X to −1 on Z, and the child's *basis* turns with it, not only its position); that the product associates the same way three levels deep; that `Transform3D.scale` composes as `S * R` and not `R * S`, which no test and no production caller had exercised at all; that `math3d.eulerQuat` is `h3d.Quat.initRotation` to nine matrix entries at three angles at once; and that a write to one node reaches its whole subtree, four levels down, without reaching a sibling subtree or its own parent.

**Three controls, because a green oracle proves nothing until it has been made red.** Making `syncWorld` compute `parent * local` reddens four cases (`child-under-rotated-parent`, `three-level-chain`, `non-uniform-scale-under-rotated-parent`, `rotating-a-parent-after-a-sync-turns-the-child`). Making `composeTransform` scale columns instead of rows — `R * S` — reddens `scale-is-prepended-to-rotation` and only that one, because it is the only case whose scaled node also rotates. Deleting the line in `syncWorld` that marks a changed node's children reddens exactly the three propagation cases that cross a level.

**What it still does not cover.** Heaps' own `syncRec` is out of reach headless: it needs an `h3d.scene.RenderContext`, which only `h3d.scene.Scene` builds, and `new h3d.scene.Scene(false, false)` calls `hxd.Window.getInstance()` — measured on node, `ReferenceError: window is not defined`. What runs is `getAbsPos()`, whose private `syncPos()` (`Object.hx:855`) recomputes the parent chain and yields the same *values* `syncRec` would. So the oracle asks for values and never for the *count* of nodes a sync recomputes: `syncPos` is lazy along one chain where `syncRec` and this port's `syncWorld` both descend the whole tree, and comparing those counts would compare two Heaps functions rather than the port against Heaps. Two consequences of that are therefore still source-derived: Heaps' `syncRec` returns early for an invisible or culled subtree and leaves its `absPos` stale where this port's `syncWorld` refreshes it regardless, and `emitRec` — the set of (mesh, material, world) a scene yields and the order it yields them in — is not asked at all. `emitRec` waits for M7 deliberately: "sibling order is draw order" is a claim about Heaps as much as about this port, but M7 is the milestone where sorting arrives and tree order stops being the answer, so that is when the comparison starts to matter.

### Running the Haxe side

Haxe was installed during this arc (scoop): `haxe 4.3.7`, `neko 2.4.1`, `haxelib git heaps ...
2b84cc2` plus `format 3.8.0`. Use `-lib heaps -lib format`; **do not** use the clone at
`~/projects/heaps`, which is 18 commits off the pin.

Three traps, one of which no document had:

- `haxelib` prints nothing and exits silently unless **`~/scoop/apps/neko/current` is on PATH**.
  It is `0xC0000135`, a missing `neko.dll`, not the segfault `SCENE-SCALE.md` §204 diagnosed.
  So every oracle invocation needs `PATH="$HOME/scoop/shims:$HOME/scoop/apps/neko/current:$PATH"`.
- §204's warning is real and I walked into it while debugging: **node to a pipe reads as a hang**.
  Redirect to a file, including when tracing with `sh -x`.
- **Not in §204, and the expensive one: node never exits.** Heaps' JS keeps the event loop alive,
  so the program prints every value and then sits there forever, output already complete. The
  generated main ends with `js.Syntax.code("process.exit(0)")` and the node call is wrapped in
  `timeout` so a future recurrence fails loudly instead of hanging. This is what made item 1 cost
  more than "just wiring".

Two things about the case format that will bite whoever adds cases: the generated MetaScript
lands in `out/tmp/oracle/`, so preludes import `../../../src/...`, three levels up; and the two
sides of a case must emit the **same number of values** under the same id, so a six-value Heaps
row and two three-value port rows silently mismatch rather than failing usefully.

### M6 as built

- **`scene.ms` is the tree, and the renderer never walks it.** `Object3D` carries `kind`, `flags`, `parent`, `payload`, `local`, `world` and `children` — the small node "Data types" asked for, against `Node2D`'s 71 fields. `Transform3D { position, rotation, scale }` is one field because every pass that reads one reads all three, and `world: Mat4` is another. Heaps' `h3d.scene.Object` allocates four times (itself, `absPos`, `qRot`, `children`); here only the node's `children` array allocates, and only when the structure changes — which was **false as first written**: `collect` and `refresh` bound each node's children to a `Vec` local, CODE-STYLE section 5's copy trap, and so allocated once per node visited per frame. Both now index through the field, and the `allocation` gate stage holds it. `MeshInstance { mesh, material }` is the Mesh side table; lights get their own in M7 rather than fields on the node.
- **`calcAbsPos` is `local * parent` in row-vector order**, Heaps' `multiply3x4inline` (`Object.hx:772`), via `Mat4.multiplyAffine`. `sync` is `syncRec` minus the animation, follow, culling-collider and fixed-position machinery M6 has no use for: it descends from the root, recomputes `world` only for nodes carrying `posChanged`, propagates the flag to their children and clears it on the way down (`Object.hx:833-841`). A test asserts a parent's quarter-turn takes a child at +X to −Z, which is what `parent * local` would get backwards.
- **Three things read out of Bevy at `2bddbdfd7` rather than invented.** Children are a contiguous `Vec<int32>` with no sibling links, the same reason the draw list is flat (`bevy_ecs/src/hierarchy.rs:154`); descent uses an explicit stack, preallocated as nodes are added, not `firstChild`/`nextSibling` pointer-chasing; and a node is addressed by index plus generation with a dense LIFO free list, a generation that would wrap retiring the slot instead of aliasing it (`entity/mod.rs:710-755`, `:885-892`). A silently reused node id in a scene graph is unfindable from its symptom, so the test that an old id is refused after its slot is reused is one of the load-bearing ones.
- **The renderer consumes a draw list, and only structural change rebuilds it.** `collect` is the walk `emitRec` does every frame in Heaps; here it runs when the structure moved and writes into a `Vec<DrawItem>` the caller owns. `refresh` is the steady path: it syncs, then rewrites `world` and `mesh` in place for every visible mesh node, because the tree and the list are in the same order. Emptying the list pops rather than assigning a fresh array, so the capacity survives. The renderer still works, and is still tested, with no scene at all.
- **M6 introduced the lit model block.** Its row-major upload against GLSL's column-major read is the convention `viewProj` already used, and `Program.Lit` remains the only program that needs per-object placement; billboards carry world-space instance roots and screen programs have no object transform. M8 expands this block with the inverse-transpose normal transform rather than leaving M6's uniform-scale assumption in place; see "M8 as built".
- **The campfire is a tree, and the spike is gone.** `src/examples/campfireScene.ms` no longer holds a merged world-space `MeshData` or a hand-pushed draw list. Each of the ground, the 26 stones and the 3 logs is modelled at the origin, unturned, and placed by its node: `position` is the base and `rotation` is `eulerQuat(tilt, yaw, 0)`. That ordering was measured, not reasoned — `toWorld` tilts about X and then yaws about Y, and against the builder's own matrix that quaternion agrees to **1.19e-7**, one float32 ulp at that magnitude, while the three other orderings are wrong by 0.78 to 1.5 (`out/tmp/quatProbe`). The logs hang under their own group rather than off the root, so the tree carries a real two-level product.
- **Byte-identity, and what it cost to believe it.** The worry was that moving placement onto a matrix would change the picture: `toWorld` computes `base.x + local.x*yawCos + (…)*yawSin` and a matrix computes the same terms with `+ base.x` last, so the translation moves from the front of the sum to the back and float32 addition is not associative. That is true of the **vertex floats** — `out/tmp/worldProbe` shows 4 of a box's 5 corners differing by 1 or 2 ulps, `0.12782013416290283` against `0.12782010436058044`. It is not true of the **image**, and the difference between those two claims was measured rather than argued: routing `toWorld` through a `Mat4` left all six configurations byte-identical, and the control (`+0.01` on the same term) fails every one of them loudly at AE 1820, 1848, 1748, 1836 and PAE 59110. So there is no baked fallback and no divergence to carry: the campfire is placed by matrices and the six baselines are untouched.
- **On fused multiply-add, and how far that answer reaches.** Adding the model matrix while every item still passed identity proves nothing about contraction, because `1*x + 0*y + 0*z + 0*w` is exact whether the compiler fuses or not. Only a non-identity rotation discriminates — and **the campfire has fewer of those than the node count suggests**. `layoutStones` gives every stone `tilt: 0.0` and 22 of the 26 `yaw: 0.0`, so 22 stones and the ground plane carry an exactly-identity 3×3 with a translation, and by the argument in the previous sentence they settle nothing. The discriminating set is **7 boxes** — the 3 logs, which have both yaw and tilt, and 4 stones at yaw 0.02, 0.05, 0.10 and 0.12 radians — which is 140 of the 584 vertices. Those came through byte-identical, so on D3D11 the shader compiler does not contract in a way that moves a pixel *for rotations of that size*, and neither `precise` nor `invariant` is needed here. That is a narrower claim than "the compiler does not contract", and it is the one the evidence supports. **On D3D11**, which is the whole of the evidence — see the scope note above.
- **A seventh capture configuration**, `campfireSpinCapture`, turns the log group 0.11 rad every frame. It exists for what the other six cannot reach: they all render a scene placed once that never moves, so none of them exercises a node changing after setup or a child whose world matrix is its parent's times its own. Its baseline is **new** at M6, which is not re-baselining: comparing the same frame with the spin on and off isolates the rotation at AE 160, 548, 484 and 344 pixels, and the six standing baselines stayed byte-identical because an identity parent multiplies exactly.
- **`tests/PENDING3D.md` on rexa's rule.** A listed case that stops holding fails the run, and its row is deleted in the same commit as the fix. Eleven rows, each with a `// PENDING3D: <id>` sentinel at the site or a named sentence in this document. The `pending` gate stage fails in **both** directions — a row whose sentinel is gone is a graduated entry, a sentinel with no row is an undocumented divergence — and both directions were verified by breaking them.
- **A bench stage, and the number it first produced was wrong.** Frame-state growth is gated at zero: over 300 frames the draw list, node table, descent stack, uniform pool, mesh table and pipeline cache all grow by nothing. **That is not the same claim as "nothing in `frame` allocates", and M6 shipped believing it was.** An allocation that does not move a length is invisible to it, which is exactly how a per-node `msArrayCopy` in `refresh` survived a green gate until the review read the emitted C. The claim now has its own stage: `allocation` greps the emitted C for `msArrayCopy` inside `syncWorld`, `collectDrawList` and `refresh`, is deterministic, and fails — verified by putting the copy back — naming the function. The DRC ledger (`-DMS_DRC_LEDGER`) was tried first and rejected — it counts typed ref objects and reports `alloc=0` for a `Vec` and for a string, so on a renderer built from structs and `Vec` it would have passed while measuring nothing. The first wall-clock number, 6.06 ms/frame at a 0.02% coefficient of variation, was **vsync**: its reciprocal is 165 Hz exactly. Timing inside the frame callback instead gives the real figure, **0.0643 ms of CPU per frame** over ten runs, sd 0.0017, **CV 2.64%, spread 8.6%** — measured after the copy trap above was removed, which both lowered the cost (from 0.0727 ms) and steadied it, because the malloc and free were the noisy part. Before that fix a second ten-run sample taken by the reviewer gave CV 6.9% and spread 23.6% against the first sample's 4.38% and 14.9%, which is its own lesson: one sample of ten is not a variance. There is still no millisecond threshold in the gate, and the figure above is not yet a licence for one — a threshold needs the spread of *several* samples, not the best of two.

**Two things `remove` does not do.** It frees the node slot and bumps the generation, but it never reclaims the `MeshInstance` row in `scene.meshes`: `addMeshNode` pushes a fresh row on every call, including into a reused slot, so churning *n* mesh nodes grows that table by *n* forever while `nodeCount()` stays flat. Payload indices stay valid, so it is a leak rather than a correctness bug, and compacting it later needs a remap pass because `payload` is a raw index with no back-pointer. And a slot whose generation would wrap is retired rather than reused — that half was right — but M6 first shipped it without also invalidating the id, so `isLive` kept answering true for the retired node and every guarded entry point let a caller through, including adopting a child under a node unreachable from the root. The generation is now zeroed on retirement, which no id is ever issued with.

**Still missing after M6.** The campfire still cannot rebuild its billboard corner buffer, grass and flame instance buffers, or its two generated textures after a context loss, because regenerating them re-rolls the shared `nextRandom()` and would change the image; it needs kept pixels or a reset seed, and it is `example-billboards-not-rebuildable` in PENDING3D. `GpuMesh.generation` still says the wrong thing for an externally-owned mesh, with `isStale`'s length check on a sibling table standing in for an ownership field. `staleMeshes` still duplicates `rebuildMeshes`' loop. No node has a bounds, so nothing culls and M10's picking has nothing to test against. `remove` never shrinks `nodes`, so a scene that churns nodes keeps its high-water mark — right for this workload, wrong for a long-lived editor. And the draw list is emitted in tree order with no sorting: `Phase` exists on the material and `sortBackToFront` exists in the renderer, but the scene uses neither, which is fine while everything is opaque and is the first thing M7's lights and any transparency will break.


### M7 as built

- **A light is a node whose payload indexes a side table, not a field on the node.** `NodeKind.Light` with `lights: Vec<LightInstance>` (`kind`, `color`, `radius`, `power`, `priority`) is the same cut `meshes: Vec<MeshInstance>` already had, so `addLightNode`, `setLightPower` and `setAmbient` are the only new entry points and the tree's allocation profile did not move: 36 nodes, still 32 draw items, because a light is not a drawable — Heaps' `h3d.scene.Light` is an `Object` with an emit hook, not a renderer input. The campfire's moon and fire are `addLightNode` calls; the flicker that used to rewrite a hand-built `lightParams` array now does `setLocal` + `setLightPower` and nothing else knows a light moved.
- **`collectLights` is `fwd.LightSystem.computeLight` cut to one global block: ambient, one directional, four point slots.** It syncs first (a light's position and direction are its world matrix, so collecting before the sync reads the previous frame), walks the same explicit stack as `collectDrawList`, sorts the point lights by priority with a stable insertion sort, and writes the count into `ambient.a` — the shader loops `int(ambient.a + 0.5)`. Priority-descending is `sortLight`'s first key; the tie-break is this port's own — Heaps ties on `objectDistance` (`LightSystem.hx:52-55`), this port keeps declaration order, which only affects float summation order in the shader's sum. Also cut, both deliberate: a directional's `priority` is never read (the slot is singular), and `cullLights`' frustum drop by `cullingDistance` is not ported — visibility is the caller's flag here. A second visible directional or a fifth visible point light is `LightError.TooMany*`, an error the caller sees, where `fwd.LightSystem` silently keeps its top N: a shader quietly lighting less is the failure this port refuses. The divergence from Heaps' parameter shapes — `radius` and `power` rather than `params` (constant, linear, quadratic) and an unfolded DirLight intensity — is deliberate and written down (`light-params-divergence`, PENDING3D): this shader quantizes total energy before multiplying color, and folding power into color would quantize at a different place.
- **The directional light's direction is its front vector negated, set by the shortest-arc quaternion.** `fwd.DirLight.emit` reads `absPos.front()` normalized and negates; here "front" is the transformed **+Z** axis (`transformDirection(vec3(0,0,1), world)`), where Heaps' `Matrix.front()` is its **+X** row — Heaps is X-forward, this frame is Y-up right-handed with Z-forward, so a rotation copied verbatim from a Heaps scene aims a directional 90° off. The campfire's moon is `quatBetween(vec3(0,0,1), -moonToward)` (`math3d`, half-angle form, no arccosine — 3 tests, including the opposite-vector 180° case and the dot-past-−1 rounding case), and `collectLights` writes `front.scaled(-1).normalized()` so the block holds the vector pointing at the light, which is what `dot(n, dirLight.xyz)` wants.
- **The light block grew from 20 to 44 floats, and the layout is a fact about the generated header, not about std140 intuition.** `vec4 ambient, dirLight, dirColor, pointLight[4], pointColor[4]` packs to c0..c10 — one `vec4` per light per array, `packoffset(c3)`/`packoffset(c7)` in the HLSL — so the stride within an array is four floats. It was first written as eight, and the test suite caught it before the GPU did: `index 28 out of bounds (length 28)` is the color write landing past the end of a 28-float buffer. The toon levels and the grass tint moved out of the light block into the material's own (`toonParams`, binding 3; `spriteParams`, binding 2), so a material now carries its ramp the way Heaps' Material carries a Pass, and the renderer reserves and uploads it like any other block.
- **Byte-identity held where re-baselining was expected — and the reason is measured, not lucky.** The moon direction `(0.35, 0.9, 0.25)` has norm 0.99750, so normalizing it moves the vector by a quarter of a percent, and no quantization threshold crossed: all seven configurations stayed byte-identical to their M6 baselines with no baseline touched. Because "the lights did not change the image" and "the lights are not wired to the image" look identical in a `cmp`, the control was run: moon power 0.22 → 0.5 changes **225 928 px (24.51%)** at frames 1/6/11/16 of palette-off (AE, `magick compare`), power 0.22 changes 0. The lights drive the shader; the values arriving are the old values. Re-derivable: `sed -i 's/power: 0.22,/power: 0.5,/' out/tmp/campfireScene.ms`, rebuild and run `out/tmp/capture/campfireCapture.ms` with `CAPTURE_PREFIX=out/tmp/capture/ctrl`, then `magick compare -metric AE out/tmp/capture/before_1.ppm out/tmp/capture/ctrl_1.ppm null:`.
- **The campfire's own GPU resources rebuild from kept CPU copies, and nothing re-rolls the RNG.** `tuftPixels`/`flamePixels` are snapshotted after each texture build (the shared scratch is overwritten by the second build), `grassInstances` was already kept, the flame instances are `deterministicFlameInstance(frame)` — a pure function, no RNG — and the corners are a const. `forceRebuild` destroys the buffers, views, images and sampler it owns, re-makes them from those copies, and writes the new handles back into the external meshes and materials; `randomState` is untouched, and the frames after the mid-run rebuild are byte-identical to the frames before it (`campfireRebuildCapture`, rebuild at frame 3, captures 6/11/16). The destroy-first shape is not the renderer's context-loss shape — the renderer *drops* handles without destroying, because after a real loss they name dead objects (M3) — it is the shape of a rebuild simulated on a live context, where allocation without destruction exhausted sokol's buffer pool (`BUFFER_POOL_EXHAUSTED`, five allocations into the first rebuild). Both shapes are written here because a reader who copies one for the other gets either a leak or a validation error. `example-billboards-not-rebuildable` is paid and its row is gone from PENDING3D.

**Measured at M7, stated as of tree `3507f613`** — the tree of *refactor(void3d): the lit shader's moon local names the lambert term it holds*, the milestone's last code commit (the review's fixes included): **617 tests** (604 before M7: 10 scene tests, 3 quaternion tests), 30 oracle cases still agreeing and 3 diverging as declared, seven byte-identical configurations, no baseline replaced, PENDING3D at 10 rows (the review added `scene-side-tables-never-shrunk`), 36 nodes / 32 draw items / 36 meshes / 4 pipelines, bench zero growth over 300 frames at 0.0616 ms CPU per frame, arm64 `libVoidAndroid.so` 2 376 056 bytes (2 319 400 at M6 — the light block, the two material blocks and the rebuild path are the delta). ### M9 as built

- **One module, `animation.ms`, three types.** `AnimationClock` is `h3d.anim.Animation`'s timing state as a value: `frameCount`, `sampling` (keys per second), `speed`, `frame` (float64, as Heaps' Float — a wallpaper clock runs for hours), `loop`, `pause`. `ObjectAnimation` is `LinearAnimation`: one `Transform3D` key per frame per track, stored track-major in one `Vec`, each track bound to a node by name. `MeshFrameAnimation` is the vertex-baked half, which Heaps does not have (it animates vertices only through `Skin`): one uploaded mesh per frame, swapped onto a mesh node with `setMeshOf`. None of the three lives on the node — Heaps keeps `currentAnimation` on `Object`; here the caller owns its animations and calls `update` then `syncPose` / `syncMeshFrame`, the pair `Object.syncRec` runs, so the node stays the small node "Data types" asks for.
- **The port, and where it came from.** `update` is `Animation.update` minus events and `onAnimEnd`: a value clock has no callback to call, so it returns whether the sampled keys moved, which is what a host on the V6 on-demand pacing needs to decide whether to `markChanged`. `keys()` is `getIFrame` plus the clamps that open `LinearAnimation.sync`; `Transform3D.blendTo` is that function's blend — translation and scale as `f1 * k1 + f2 * k2`, rotation by nearest-hemisphere lerp then normalize, `math3d.nlerp`. `setFrame` is `Animation.setFrame`'s two `while` loops in one step, so a positive exact multiple lands on `frameCount`, and a clock at `frameCount` shows the last key whether or not it loops — `sync`'s `frame >= frameCount` clamp (`LinearAnimation.hx:153`); a loop's next `update` wraps it to 0 first. All three oracle cases agree with Heaps. `bindTracks` is `Animation.bind` over `findByName`, resolving every name before it writes any target, so a failed rebind leaves the previous binding whole. `syncPose` keeps Heaps' `syncFrame` cache as a `KeyPair` compare, so a pose that has not moved writes no node and marks nothing for `syncWorld`; it checks every target is live before consulting that cache, and `forgetSync` drops it when something else has written one of its nodes. `update` refuses a non-finite advance and leaves the clock where it was; a one-key clip never reports a change; a clock with no frames is refused by everything built on it.
- **Stepped sampling is this port's addition.** `Interpolation.Step` floors the frame before sampling, so a key is shown whole and never blended — the brief's 12 fps look — and `update` then reports a change only when a key boundary is crossed: 30 updates at 1/30 s on a 12-key, 12 fps clock report exactly 12 changes (tested). Mesh frames only step (`InterpolatedMeshFrames` otherwise): blending two baked frames would mean writing vertices into a live buffer every frame.
- **Three divergences, each written down, two measured against real Heaps.** `tests/oracle/anim3d.cases` runs fourteen cases through `LinearAnimation` at `2b84cc2`; eleven agree and three diverge as declared. The clock never samples outside its keys (`anim-never-extrapolates`): a one-shot inside its last interval holds its last key, where Heaps' `getIFrame` steps back a key and the weight runs past 1 — keys 0, 10, 20 at frame 2.5 give Heaps **25** and this port **20** — and a frame below 0, which a negative speed reaches, holds the first key where Heaps' truncating `Std.int` gives a negative weight — keys 0, 10 at frame −0.5 give Heaps **−5** and this port **0**. A negative speed on a loop never wraps, in Heaps or here: `update` wraps only past the end. A pose replaces the node's local transform, as a glTF channel does, where Heaps writes `defaultTransform` and prepends it to the object's own x/y/z — an object at x = 5 posed to x = 1 lands at **6** in Heaps and **1** here (`anim-pose-replaces-local`). `bindTracks` refuses a track whose name is missing where Heaps drops it and plays the rest (`anim-missing-target-refused`, source-derived). The control: swapping the blend to `slerp` mismatches `rotation-is-nlerp` (m11 0.9553 against Heaps' 0.9574); the other two rotation cases blend at the midpoint, where the two agree, so they cannot tell them apart.
- **Not ported**, none of it needed by the milestone: events (`addEvent`, `onEvent`), `onAnimEnd`, `LinearAnimation`'s alpha, UV and property curves, the single-frame-track shortcut, `BufferAnimation`'s float buffer with its `xyz`-only quaternion (an HMD storage detail — a `Vec<Transform3D>` is already one flat buffer), `decompose`, `SimpleBlend`, `Transition`, `SmoothTarget`, `BlendSpace2D` and `Skin`.
- **Baked frames never re-upload, which is what answers M5's leak.** `addBakedFrames` always takes `frames.length` contiguous slots starting at the context's mesh count; a refused upload keeps its CPU data for the next rebuild and the call reports it. M5 kept `recomputeBounds` and flagged `uploadMesh`'s missing destroy for "a vertex-baked frame swapping positions under a mesh that keeps its indices". M9 does not take that path: `addBakedFrames` uploads each frame once through `addMeshData`, so each is an ordinary rebuildable mesh with its own bounds (what M10 will pick against), and a frame change is one `setMeshOf` — no buffer is written in the frame loop, and nothing leaks. `checkBakedFrames` holds every frame to frame 0's vertex count and exact indices, so a swap moves vertices and never changes which triangles exist. The cost is one index buffer per frame, 3 kB at a 500-triangle budget. `upload-mesh-leaks-on-replace` stays in PENDING3D for whatever first re-uploads a live mesh.
- **The campfire runs on it.** The flame's atlas cell was `(frameIndex / 4) % 4` fed to `setMeshOf`; it is now a `MeshFrameAnimation` stepping 0.25 keys per frame. The spin capture's log group was turned by hand each frame; it is now an `ObjectAnimation` of 32 stepped keys at 0.11 rad per key, which then holds — the captures end at frame 16. One stone goes through `addBakedFrames` with two identical frames swapped by a `MeshFrameAnimation`, so upload, swap and the mid-run rebuild of baked frames run in every capture while the image cannot change; the swap itself is what the flame shows. The example's clock runs in frames, not seconds — `update(clock, 1.0)` per frame — because the captures are frame-indexed.

**Acceptance, byte-identical, with controls.** All seven capture configurations — 28 frames against 24 baselines — are byte-identical to their M8 images with no baseline touched, including `campfireSpinCapture`, whose rotation now passes through `blendTo`'s renormalization. Because "the animation reproduced the old motion" and "the animation is not wired" look the same in a `cmp`, both halves were broken on purpose in `out/tmp/campfireScene.ms`: keys at `0.11 * (i + 1)` move `campfireSpinCapture` at all four frames (AE 116, 124, 144, 132 against `m6spin_*`); a flame at 1/3 key per frame moves frames 11 and 16 of palette-off (AE 92, 120) and leaves 1 and 6 alone — frame 6 because six additions of 1/3 sum to 1.999…, which floors to the key 0.25 would also give.

**That last number is a caveat for any stepped clock.** A key boundary is decided by `floor` on an accumulated float, so a rate that is not a binary fraction can show a key one update late. The campfire's 0.25 is exact; Hibernal's 12 fps driven at 1/30 s accumulates 0.4 per tick, and the 30-tick test lands on 12 changes, but that is a measurement of those two numbers, not a guarantee for every pair.

**The allocation stage was blind in two ways, and both are closed.** It read the newest emitted C in the object cache by mtime: after an oracle build that file had no body for `refresh` or `collectDrawList`, and after a revert it held the reverted code — either way a pass. And it matched `msArrayCopy`, while a `Vec` of structs with owned fields copies through `<T>ArrayCopy` (measured: `ObjectTrackArrayCopy`). The stage now emits the campfire bench entry's C with `--emit=c` into fixed names, fails when a listed function has no body, matches both spellings, and covers `update`, `keys`, `blendTo`, `syncPose`, `syncMeshFrame`, `setLocal` and `setMeshOf`. The bench now turns the spin on, so `syncPose` runs across its 300 frames. Controls: green on this tree; red naming `syncPose` with a copied-and-written `Vec<ObjectTrack>` injected; green after the revert; red on a misspelled function name.

**Measured at M9, as of code tree `98781380` (the review's fixes included):** 654 tests (627 before M9, 27 new), 41 oracle cases agreeing with real Heaps and 6 declared divergences over three files, 28 byte-identical frame comparisons, PENDING3D at 14 rows, zero frame-state growth over 300 frames with 37 meshes of which 31 rebuildable, one bench sample of 0.0695 ms CPU per frame (one sample, and the bench now animates the spin, so not comparable with M7's 0.0616), arm64 `libVoidAndroid.so` 2,496,040 bytes — 110,416 more than M8, not yet attributed.

**Still missing after M9.** No glTF animation is decoded: M8 refuses morph targets, and T1's generator does not exist, so whether its nine baked animations arrive as morph targets, one mesh per frame, or node channels is undecided (Open questions). Nothing times a clock against a real host: the campfire drives it in frames, and no capture runs at seconds-based pacing.

### M10 as built

- **Four pieces, each the Heaps function it names.** `ray.ms` is `h3d.col.Ray`: `fromPoints`, `transformed` (`Ray.transform`: the origin as a point, the direction through the 3×3, renormalized) and `pointAt` (`getPoint`). It left `camera.ms`, and `rayFromScreen` now ends in `Ray.fromPoints`, as Heaps' does. `Bounds.rayIntersection` is Heaps' slab test. As in Heaps it answers a negative entry for a box behind the ray or around its origin. `MeshData.rayIntersection` is `PolygonBuffer.rayIntersection`, Möller–Trumbore with `hxd.Math.EPSILON`, over the `Lit` vertices and uint16 indices in place. It always takes the nearest triangle (`bestMatch`), because `rayCastEventTargets` refines every hit with `bestMatch = true` before it sorts. `pick.ms` `pickNearest` is that function's non-physics branch, per mesh `ObjectCollider` over `OptimizedCollider(bounds, polygon)`.
- **`Interactive` is cut to a flag, and that is a divergence, not an equivalence.** `setPickable` sets `FLAG_PICKABLE` on any node. A hit on a mesh belongs to its nearest pickable ancestor-or-self, and `PickHit` carries that `owner`, the `mesh` node actually hit, the distance and the world point. As in Heaps, a mesh with no pickable ancestor is not tested and does not stand in front of one that is. The `pick` stage measures this: a tap through a stone that is not pickable reaches the ground, which is not pickable either, and hits nothing. Three consequences differ from Heaps, where the shape is a collider built from `getCollider()` (`pick-owner-is-a-flag`):
  - a hidden mesh under a visible pickable node is not hit, where `getCollider()` gathers hidden children;
  - nested pickable nodes give the hit to the nearest one, where Heaps' outer shape also holds the inner meshes and ties;
  - the geometry is the live tree at the tap, where a Heaps shape is a snapshot taken when it was built.
  The walk skips every subtree under an invisible node, and `FLAG_CULLED` is not read.
- **Per mesh.** The world ray goes into the node's space through `inverseAffine(world)`. A singular world matrix, such as scale 0, yields the zero matrix, so the local ray has no direction and every triangle's determinant is 0: a miss. The bounds come next: a negative entry with the origin outside the box is a miss. **A ray that starts inside the bounds still reaches the triangles, and Heaps does not do that** (`pick-origin-inside-bounds`, measured against real Heaps). `rayCastEventTargets` sets `checkInside` only on an `OptimizedCollider`, and a shape from `getCollider()` is an `ObjectCollider`, so Heaps answers −1 where the port answers 1. The same collider with the flag set by hand agrees with the port. The triangle test keeps the faces the material draws, and swaps front for back under a mirroring world matrix, because a negative determinant turns the winding over on screen (`pick-culling-follows-material`, measured: Heaps always drops local back faces). The local hit point goes back through `world`, and the distance is measured from the world ray's origin on the near plane. **That is not Heaps' order** (`pick-distance-from-ray-origin`). Heaps sorts by distance from `camera.pos`, and the M4 camera's eye is its target, in the middle of the depth range, so an occluder just in front of the eye and the mesh just behind it would swap. The test pins the port's order with the two 0.8 apart across the eye.
- **The mesh read is the node's current one.** `pickNearest(scene, meshData, materials, ray)` takes the DrawContext's two tables as spans and reads `scene.meshes[payload]` at the moment of the tap. A baked frame that `syncMeshFrame` swapped in is the geometry tested, and an external mesh (empty `MeshData`, empty bounds) is never hit. A mesh or material index outside the tables is `PickError.MeshOutOfRange` / `MaterialOutOfRange`, not a miss. `pickNearest` syncs world matrices first, as `collectLights` does.
- **The box builders faced inward on three sides, and now face outward.** `addBox`'s top, right and left quads and `addPlane`'s quad were wound clockwise seen from outside, against the counter-clockwise front `gpu3d.c` sets. The front and back quads were already right. The campfire draws them with `Face.None`, so no image showed it; the triangle test found it. They are rewound by reversing each quad's corner order, and **all 28 capture frames stayed byte-identical**: a triangle's edges and its vertex attributes are the same in either order. "every face addBox and addPlane build faces outward" tests all five sides and the plane under both cullings.
- **`ray-bounds-parallel-on-face`**, measured against real Heaps. A ray with a zero direction component on an axis, running along that axis's face plane, divides 0 by 0 in Heaps. `hxd.Math.min`/`max` return their first argument against a NaN, so on the max face every such ray misses and on the min face every one hits. The port counts both faces as inside the slab. `bounds-ray-on-max-face-crossing` gives Heaps 0 and the port 1; `bounds-ray-on-min-face-outside` gives Heaps 1 and the port 0.
- **Not ported:** `Interactive`'s events, cursor, `priority`, `preciseShape`, `propagateEvents` and `showDebug`; the all-hits list `rayCastEventTargets` returns (only the nearest is kept, so nothing allocates); `bestMatch = false`; `Bounds.transform3x3` and `intersection`, which the pick path does not need; `Ray.collide`, `distance`, `intersect` and `collideFrustum`; `Polygon`/`TriPlane` (`PolygonBuffer` works on the index buffer directly and needs no per-triangle precompute); every collider but bounds and triangles; hlphysics.
- **No second screen mapping.** The campfire keeps the `CameraView` and the shifted `LowResView` the last frame was drawn with. `campfireTap(x, y)` takes host pixels, rows counted from the top as sokol_app and Android deliver them. It flips the row on GL, whose blit counts rows from the bottom, then calls `rayFromScreen` through that pair and `pickNearest`. `campfirePixelOf(node)` goes the other way, and is a `Result` that refuses a stale or non-mesh node.

### M11 as built

- **`particles.ms` is `h3d.parts` without the draw call.** `ParticleValue` is `Data.Value` and `EmitterShape` is `Data.Shape`, both as closed unions (`match (kind: …)`). `EmitterState` is `Data.State`, with `defaults()` as `setDefaults`. `updateEmitter` is `Emitter.update` with `initPosDir`, `initPart` and `updateParticle` in Heaps' order, so every random value is drawn at the point Heaps draws it. `writeInstances` is the half of `Particles.draw` that fills the buffer. It evaluates `globalSize` on every call, before it returns on an empty emitter, as `Emitter.draw` does (`Emitter.hx:272`), so a random `globalSize` consumes the sequence exactly as Heaps does. The emitter is a value the caller owns, as M9's animations are: it is not a node kind and has no side table. It takes the world matrix of the node that places it, and that node carries a stream mesh (below) the draw list already knows how to draw.
- **Frame, randomness and time.** Heaps is Z up and left-handed. Exchanging y and z maps it onto this frame, so the cone and the line point up +Y, the disc lies in XZ and gravity pulls along −Y. Heaps reads `Math.random`; the emitter owns an xorshift32 read as 24 bits (`ParticleRandom`), seeded by the caller, so a run is deterministic and the oracle can hand Heaps the same sequence. Every time that decides an event is `float64`, as Heaps' `Float` is: emitter time, the emission count, particle time, the life factor, `globalLife`, burst times and colour-key times. They were `float32` first, and the oracle measured the cost: the emission count and the moment a particle dies each drifted by one (`random-lives-keep-order` kept 13 particles against Heaps' 12, `color-keys-light-alpha` 9 against 8). The design review then found burst and key times still `float32`, and measured it: a burst at 0.1 fires one update late, because 0.1 in `float32` is 0.10000000149 (`burst-at-a-tenth` now agrees). Positions, sizes and colours stay `float32`, the vertex format.
- **Not ported:** `VPoly`, `VCustom`, `SCustom`, `ratio`, `rotation`, `frame` and textures, `emitTrail`, `collide` and `Collider`, `delay`, the `update` callback, `Emitter.speed`, `setState` on a live emitter, `offsetParticles`, `alloc`/`add`, `SortMode` and `BlendMode`. The pool of `Particle` objects is a dense array of capacity `maxParts`, fixed at `create` in `capacity` so that a caller raising `state.maxParts` later cannot outgrow it, compacted in order as particles die, which is the order Heaps' list keeps.
- **Three divergences, one measured.** A particle draws its random values again every life, where Heaps' pool hands a reborn particle the values of its last one (`particle-random-per-life`: 0.18018 in Heaps for both lives, 0.16936 here for the second). A particle is a camera-facing square of side `size × globalSize` in world units, where Heaps' default sizes it in clip space with a factor of 0.4 (`particle-size-world-units`). The program discards below half alpha and writes depth instead of blending and sorting (`particle-alpha-tested`).
- **Two names moved for the compiler.** Heaps' `update` is `updateEmitter`, because `animation.ms` exports `update(ref clock, …)` and two `ref` free functions with one name resolve to the wrong one silently (`particle-update-name-collision`, card `2026-09-20-ref-receiver-not-an-extension.md`). The random state is the field `sequence`: a field named `random` in the `Result.ok({…})` of `ParticleEmitter.create` made std's `Math.random` reachable, whose body calls an undeclared `time()` and fails clang (card `2026-09-23-literal-key-reaches-std-function.md`, Compiler notes).
- **Instance data: a stream mesh, not an `InstanceData` sibling** (Open questions, answered). `draw.ms` `addStreamMesh(context, capacity)` puts a `GpuMesh` whose `instanceCapacity` is non-zero into the same table. Its instance buffer is made once at that capacity (`gpu3dMakeStreamBuffer`, sokol `dynamic_update`), and `writeStream` replaces its contents and sets the instance count, one `sg_update_buffer` per frame. A write the driver refuses (a buffer that is not valid, or more floats than it holds) is `StreamError.BufferRefused` and leaves the stream drawing nothing; a remake that gets only one of its two buffers destroys that one. It keeps no CPU copy: its owner holds the state it is written from and writes it every frame it draws, so a kept copy would be stale by construction. After a context loss, the loop that re-uploads meshes (`rebuildMeshes`) remakes a stream's buffers empty, with zero instances. A `writeStream` that finds its handles stale remakes them first, so the write after a loss is also the rebuild. The buffer is `dynamic_update` rather than `write_transient`: a transient buffer must be written every frame it is bound, and a host on the on-demand pacing redraws for a camera move while a paused emitter writes nothing new.
- **The particle program** (`particleVs`/`particleFs`) runs on the `Billboard` layout. Its corners sit around the root at ±0.5, as `Particles.hx` writes them, and each instance is eight floats, root and side then rgba, unlit. `gpu3d.c` asserts that its attribute slots are the billboard program's. Adding it found two defects in the bridge, both fixed at the source:
  - `PipelineCache.shaders` was sized by a hand-kept `PROGRAM_COUNT = 4`, so the fifth program indexed past it. The count is now `GPU3D_PROGRAM_COUNT` in `gpu3d.h`, the constant `gpu3d.c` asserts the `PROGRAMS` table against.
  - The core applied the camera and light blocks to every scene item. The particle program declares no light block, and sokol panics on `sg_apply_uniforms` for an undeclared slot. The cache now reads each program's declared slots off its shader description when it makes the shader (`gpu3dUniformSlotMask`), and `drawItem` applies a pass-wide block only where it is declared. That is reflection from the generated header, not a second hand-kept table.
- **Saturation is a look parameter; the palette swap already was one.** `PixelArtLook.saturation` is `h3d.Matrix.colorSaturate`: `rgb × (1 + s) − luma × s` with Heaps' `lumR/G/B`, where 0 leaves colour alone and −1 is grey. The post pass applies it after fog and before the palette LUT, so a greyed frame is still quantized to the palette. At 0 it is skipped, so the existing frames did not move. It sits in a new `colorAdjust` vec4 of the post block, which grew from 20 to 24 floats. The swap is M3's `setPalette`, which refills the LUT on the CPU and uploads it on the next frame. Measured: **2.33 to 2.46 ms** per refill at 16 levels and 21 colours (desktop, debug build, 200 refills per run, three runs). That is cheap for a day/night or seasonal change and too slow for a per-frame blend.
- **Effects stay a closed set, as fields of the look** (M3's question, answered). Heaps' `RendererFX` is an open interface because a Heaps program can bring its own hxsl. Here a program is a member of the closed `Program` enum, compiled by sokol-shdc into `gpu3d.c`, so no caller can bring an effect void3d does not already know. An open `interface` with function-typed fields would cost an indirect call per effect and a refcounted object, and buy nothing. Everything M11 needs folds into the one post pass M3 chose (outline, fog, saturation, palette), so the set is data, not a list. When an effect needs its own pass (bloom), it becomes a member of a closed union the preset matches on, not an interface.
- **The campfire has snow and embers, off unless configured.** `configureCampfireParticles(true)` adds two emitters, each on a stream mesh under its own node:
  - a disc 6 units up: 45 per second, 7 s lives, capacity 400, wind drift, fading;

  Both run for eight seconds of 1/30 s steps at setup, so snow is already falling in frame 1. `configureCampfireLookSchedule(true)` swaps to a cold palette at frame 5, sets saturation −1 at frame 10 and puts both back at frame 15. Every preset number lives in the example: nothing in `src/void3d` is named snow, ember or fading.
- **The scene's side tables shrink** (`scene-side-tables-never-shrunk`, which M7 assigned to this milestone). `remove` swap-removes a mesh or light node's row and repoints the node that owned the last row, through `meshOwners`/`lightOwners`. M11 adds no table, but it was done here rather than left: a wallpaper that adds and removes harvest objects for days is the churn the row describes, and the fix is local to `remove`. Draw order does not change, because every reader walks the tree and reads `payload`. The row is deleted.

### M12 as built

- **Saturation is a lit-material parameter, applied to the material's colour before the lights.** The lit program reads it at `TOON_SATURATION` of the material's own block, the vec4 whose `TOON_LEVELS` already held the toon ramp levels, so the block keeps its size and layout and a caller that writes `[levels, 0, 0, 0]` sees no change. It greys `baseColor`, and the ambient and directional light are then applied to the grey. The point lights are not: `litFs` adds them without multiplying them by the material's colour, where Heaps multiplies every light in. That is M7's, recorded now in `light-params-divergence`, and it is why a greyed object still takes a warm tint from the fire. That is where Heaps' `h3d.shader.ColorMatrix` acts when it is added to a pass. It reads and writes `pixelColor`. `fwd/LightSystem.computeLight` puts `AmbientLight` at the head of the shader list, and `hxsl/Cache.compileRuntimeShader` reverses that list, so `AmbientLight`'s `pixelColor.rgb *= calcLight(…)` runs after the pass's shaders. That order was read from the Heaps source at the pin, not run: the node oracle calls Heaps' CPU code and never runs its shader linker. A Heaps object greys by adding that shader to its material's pass. Here it greys by having a material of its own, and the glTF path already takes a material per mesh from its caller (`gltfScene.ms` bindings).
- **Greying before the lights changes little on an object whose own colour is already grey.** Measured on the campfire's stones under the palette, frame 11: at −1, greying after the lights changes 88 216 pixels and greying before them 1 648, because the colour the stones show comes from the lights. - **One formula in the shaders.** `@block saturation` holds `saturated(rgb, amount)`, which skips at 0 and otherwise computes `rgb × (1 + s) − luma × s`. `litFs` and `postFs` both include it, and `postFs` lost its inline copy. The ten standing configurations stayed byte-identical through that move.
- **The CPU reference, pinned to Heaps.** `math3d.ms` `colorSaturated(this m: Mat4, amount)` is `Matrix.colorSaturate`: it builds the saturation matrix with Heaps' `lumR/G/B` and composes it after `m` through `multiplyAffine`, which is `multiply3x4`. `tests/oracle/color3d.cases` runs six cases through real Heaps at `2b84cc2` and all six agree: the matrix at −1, −0.5 and +0.4, a colour through it, the order of composition after a scale, and the offset row after a translation. A headless test ties the scalar form the shaders use to that matrix for four amounts and two colours, to 1e-6. It checks the formula, not the GLSL.
- **The GLSL, held to the reference byte for byte.** Because the saturation acts on the material's colour, the same grey can be made on the CPU. `configureCampfireGreyGround(s, true)` greys the ground's vertex colours through `colorSaturated` and keeps the scene's material. `configureCampfireGreyGround(s, false)` gives the ground its own material at `s`. At −0.75 with the post pass off, the two draw the same frames byte for byte. The gate holds both to one set of hashes (`m12greydirect_*`), as it holds the rebuilt campfire to `before_*`.
- **Not ported, and a PENDING3D row** (`material-saturation-only`). Heaps attaches a whole colour matrix to any pass. Here a material has a saturation amount on the lit program only. Billboards and particles have none, and nothing else of the matrix (contrast, gain, hue) exists.
- **The campfire greys its ground, off unless configured.** At 0 no material is added and the ground colour is untouched, so every older configuration builds the same scene. The pool grew by one toon block to hold the ground's.

### M13 as built

- **Every light multiplies the material's colour.** `litFs` sums the ambient, the directional light and the point lights into one light and multiplies the (saturated) material colour by it. That is Heaps' default, `fwd/LightSystem.additiveLighting = true`: `AmbientLight.__init__fragment` starts `lightPixelColor` at the ambient, each light's `fragment()` adds to it, and `AmbientLight.fragment` ends with `pixelColor.rgb *= lightPixelColor`. Before M13 the point lights were added after the multiply, so a dark object took the fire's full colour and a greyed one kept the fire's colour on top of its grey; the M12 section above describes that state, and the sentence saying so left `light-params-divergence`. ### Android lifecycle (V6), alongside from M3

- The shell already renders one engine at a time through one shared EGL context (`VoidRenderer.show/hide`), so preview and live never draw concurrently; the preview uses `PixelArtSettings.preview()`.
- **Context loss, done in M3 without a device.** A view's present checks `eglSwapBuffers` (`bridgeAndroid.c` `voidPlatformSurfacePresent`); on `EGL_CONTEXT_LOST` the next frame calls `sg_shutdown`, destroys every view's surface and the context, makes new ones on the same windows (or pbuffers), runs `sg_setup` again and bumps a generation (`voidGpuGeneration`, read through `gpu3d contextGeneration`). `voidEmbedLoseContext()` forces the same path, to exercise it on a device. After `sg_setup` sokol hands out ids from fresh pools, so an old handle can name a new object: the renderer **drops** its handles without destroying them (`RenderTarget.forgotten`, `forgetGpu`, `forgetPipelines`) and rebuilds targets, sampler, screen triangle, pipelines and the palette LUT from CPU data on the frame that sees the new generation.
- **Meshes, done in M5.** A mesh added through `addMeshData` keeps its vertex and index arrays in `DrawContext.meshData`, and the core's `beginFrame` re-uploads every mesh whose `GpuMesh.generation` is older than the current context. The campfire's lit geometry is one such mesh.
- **Still missing:** void2d's own resources, and any of this on a device. The campfire's billboards and generated textures now rebuild from kept CPU copies (M7 as built) — that path is simulated on D3D11 by destroy-and-remake, since `contextGeneration()` never changes there; on GLES3 only the mesh half of the rebuild has ever run for real.
- `EGL_DEPTH_SIZE` stays 0: the scene renders offscreen with its own depth attachment, and the swapchain only receives the blit.
- Frame pacing (30 / ~10 / on demand) is the host's call; `needsFrame` says whether the next frame would differ from the last (M3 as built).

## AUDIT: corpus, oracle, QC and architecture at `07bff24` + M8 delta `d5d6c3b`

The M1–M7 audit freezes tree `4db2a22e451bd783cdad6f58c0548cd9464cd335`.
M8 landed while the audit was running and is reviewed separately below at tree
`a85508e477a974d35b78e65cff2dfbb0cf104dfb`.

**Verdict: the architecture follows this document without growing a general engine.**
`scene.ms` keeps the retained `Object3D` tree small, puts meshes and lights in side tables,
and refreshes a flat `DrawItem` list only after structural change. `renderer.ms` consumes that
list rather than the scene and owns pass ordering, while generation-tagged GPU resources keep
context rebuild explicit. The explicit traversal stack, generation IDs and zero-growth steady
path are coherent with the tens-of-objects target; columnar storage would add machinery with
no measured benefit here.

**Evidence actually held.** After supplying the ignored gate prerequisites,
`sh scripts/gate3d.sh` was green with **620 tests**, **10 PENDING3D rows**, **30 oracle cases
agreeing with real Heaps and 3 declared divergences**, **28 byte-identical frame comparisons
across 7 configurations against 24 unique baselines**, zero frame-state growth over 300
frames, and a 2,371,960-byte arm64 library. The only final skip was the physical-device run.
The scene oracle also survives fault injection: reversing `local * parent` made 4 of its 16
cases fail.

### M8 delta

The implementation keeps the intended subset narrow: one caller-owned buffer, float32
position/normal/color, uint16 indices, one primitive per mesh and node TRS. The post-delta
gate was green with **624 tests**, the same 28 frame comparisons and oracle result, and a
2,381,440-byte arm64 library.

That is not yet an end-to-end glTF corpus. The repository contains no `.gltf` or `.glb`
fixture, and `loadGltf` has no consumer outside its four hand-built unit tests. Nothing proves
the accepted subset against a real Hibernal Blender export, instantiates the decoded hierarchy
into `Scene`, uploads it, or renders it. Three fault probes also show the parser currently
accepts shapes the subset must refuse: primitive `mode: 1` (LINES) is decoded as triangles; an
accessor may read 36 bytes through a buffer view declaring `byteLength: 4`; and asset version
`"2bad"` is accepted as version 2. These are validation bugs, not future-format support.

The loader also imports `float32At` from `gpu3d.ms`; that pulls the whole sokol GPU bridge into
an otherwise CPU-only decoder. A standalone `msc test` of the loader failed to link on the
bridge's `sg_*` symbols, while the integrated suite hid the coupling by already linking sokol.
Keep the exact little-endian float conversion, but place it at the binary-loader boundary so
the glTF corpus remains headless.

**Findings, in closure order:**

1. **The visual corpus is not portable from a clean checkout.** The 24 baseline PPMs,
   `test2d.ms`, the D3D11 readback C/H files and the Android entry live under ignored
   `out/tmp`; the gate generates capture entries but not those prerequisites. A clean
   worktree therefore SKIPs every baseline rather than reproducing the pixel claim, and the
   gate is allowed to finish green with skipped stages. `docs/baselines3d.sha256` authenticates
   copies somebody already has; it does not make them available. Put the baselines and harness
   in a reproducible artifact or tracked corpus, and make their absence fail the default gate.
   **Closed after M11 (`293f115`), with no image in the repository.** The committed
   `docs/baselines3d.sha256` is now the baseline set: the capture stage hashes each frame it
   renders and compares with the manifest, a frame with no hash fails, and `GATE_ADOPT=1`
   records a missing hash. The readback harness is tracked in `tests/capture3d/`, and the
   test and arm64 entries are generated by `prepare`. A fresh worktree, after `setup.sh` only,
   ran all ten configurations green, 40 frames against 32 hashes. Controls: one altered
   hash reddens the two configurations that use it, and one removed hash reddens its
   configuration and the `manifest` stage. The PPMs in `out/tmp/capture` are now only a
   local cache for measuring a difference. A hash is as machine-bound as the image was: it is
   a claim about D3D11 on this box.
2. **M8 currently accepts non-uniform glTF scale that the lit shader shades incorrectly.**
   `loadNode` preserves any three-component scale while `litVs` uses
   `mat3(model) * normal`; `math3d.normalMatrix` already exists, and `scene3d.cases` already
   carries a non-uniform-scale-under-rotated-parent case, but no GPU test or capture connects
   them. Upload the inverse-transpose normal matrix before scene integration, or reject
   non-uniform scale loudly at import. Silent acceptance is wrong.
3. **The void3d → void2d composition boundary bypasses the shared frame lifecycle.**
   `renderer.endFrame` calls `gpu3dCommit`, and `gpu3dCommit` calls `sg_commit` instead of
   `voidCommit`; the latter owns void2d's commit hook. Use one host-owned/shared commit and
   prove two consecutive mixed frames. This is the same existing mechanism the 2D audit names,
   not a second integration layer.
4. **The captures vary configuration, not scene content.** Seven runs of the campfire exercise
   palette, post-pass, depth source, rebuild and a moving parent, but they do not independently
   cover sort modes, material multiplicity, frustum/culling, mesh topology, or light-slot
   boundaries. The light block has a wiring control but no independent Heaps/numerical oracle.
   Also, only 3 of the 10 PENDING3D rows have behavioural oracle sentinels; the rest mostly
   prove that a comment or sentence still exists.
5. **Device confidence remains explicitly absent.** The gate built arm64 and the recorded
   GLES3 image came from an emulator without a baseline. Context loss, depth-texture sampling
   and the pixel/FMA claims still need the Seeker run.

The next QC order is therefore: fix M8 validation and close or reject non-uniform-scale
normals; add one real Blender-exported asset that decodes headless, enters `Scene`, and renders
through the existing capture; make the baseline corpus clean-checkout reproducible; unify
commit and add the mixed-surface capture; then add small discriminating scenes/oracles instead
of multiplying campfire configurations.

## Open questions

- **Depth for edge detection, answered for the code, open for the device.** In the vendored sokol (read at 6c3fa5ac, unchanged at 2e75443d) `SG_PIXELFORMAT_DEPTH` is `GL_DEPTH_COMPONENT32F` on GLES3, created as a real texture when single-sampled and marked sampleable but not filterable (`_sg_pixelformat_srmd`); a shader reads it with `texelFetch` through `@image_sample_type … unfilterable_float` and a `nonfiltering` sampler, which GLES 3.0 allows for sized depth formats with compare mode off. D3D11 uses `R32_TYPELESS` with an `R32_FLOAT` view. So the renderer takes it as a setting, `DepthSource.NormalAlpha` (default, the spike's 8-bit copy) or `DepthTexture`; GL stores (z + 1) / 2, which the post pass unpacks (`depthUnpack`). On D3D11 `DepthTexture` changes about 15% of the campfire's pixels: fog loses its 8-bit banding, and the normal-edge test (`|Δdepth| < depthThreshold`) flips on sloped stone faces, peak difference 85/255. The outline thresholds were tuned against 8-bit depth, so switching means retuning them. Which source ships is decided on the Seeker with RENDERER-BRIEF §10 Q4 (`RGB10_A2` vs `RGBA8` normals); M3 depends on neither.
- **One post pass or two, answered: one.** The palette quantizes the pixel the outline and fog just produced and reads no neighbor, so it runs at the end of the same fragment (`postFs`).
- **The pipeline key is now exactly full, and the next thing that selects a pipeline needs a second word.** 64 bits: vertex layout 3, indexed 1, program 4, target formats 24, `RenderState.bits` 32 — with `LAYOUT_LIMIT` holding the layout count at 8 and `TargetLayout.formatBits` already giving `sampleCount` only four bits, so a sample count of 16 would overflow into the state field. A fourth vertex layout is fine, a ninth is not; uint32 indices would need a second bit. When one of those arrives, `PipelineKey` grows a second `uint64` and `contains` / `pipelineFor` compare both — cheap, but it should be done deliberately rather than by finding a free bit.
- **Instance data has no CPU-side owner, answered at M11 for the per-frame case.** A buffer rewritten every frame is a stream mesh: a `GpuMesh` in the same table, with a capacity and no CPU copy, remade empty by the same rebuild loop and refilled by its owner's next write (M11 as built). Static instance data (the campfire's grass) is still the caller's, kept and re-made by the example (M7 as built); an owner in void3d for it arrives with the first library feature that needs one.
- **How baked animation arrives from the exporter, open until T1 exists.** M9's `MeshFrameAnimation` takes any list of `MeshData` with one topology, and M8 decodes one mesh per node with morph targets refused. A Blender generator can bake as glTF morph targets with a weights channel, as one mesh per frame, or as node TRS channels. The first needs M8 to accept `targets` and a decoder for `animations`; the second needs only a naming convention, which belongs to Hibernal, not here. Decide with the first real export.
- **Device.** Nothing here has run on the Seeker or any other phone. The GLES3 path has run only on the Android emulator (`gles3-emulator-only`, `tests/device/README.md`): the campfire with its palette, the particles and the greyed ground. Not yet run on any GLES3 driver: a real context loss (`voidEmbedLoseContext`, simulated on D3D11 only), the depth-texture path, and the snap's remainder under GL's row order, which is tested for both row orders and seen on D3D11 only.

## Compiler notes

Hit while writing M1 to M12 and worked around in void. Entries marked **re-checked** were probed again on msc 0.2.55 (`~/.metascript/BUILD` `8cdd91c6`) on 2026-09-24; the rest were not.

- **A struct literal may leave fields out; they are zero, with no diagnostic.** `struct Point { x, y, z: int32 }` with `const p: Point = { x: 1, z: 3 }` builds and prints `1 0 3` (repro in `out/tmp/fieldRepro`). Removing `distance` from `OrthoCamera` therefore left every caller compiling while the field stayed in the struct, unread and zero; only a grep found it. The workaround is review, which is why the M4 camera's fields are all written at every literal.
- **`near` and `far` cannot be struct field names on Windows.** `windows.h` still defines them as empty macros, so `camera.near = 0.0` reaches clang as `camera. = 0.0`: `error: expected identifier`, reported at the `.ms` line with no hint of a macro, plus `warning: declaration does not declare anything` on the struct itself. Workaround: `nearPlane` / `farPlane`.
- **A struct literal in an operator's operand position is not typed by the operator**, and the checker lets it through. `const clip: Vec4 = { x: …, y: …, z: …, w: 1.0 } * inverseViewProj` passes type checking and fails in clang with `invalid operands to binary expression ('__anon4__xf__yf__zf__wn' and 'const Mat4…')`. The same literal in a typed local, then multiplied, is fine. The receiver position at least fails in the checker: `({ ...camera, farPlane: x }).resolve(…)` is `Property 'resolve' does not exist on type '__anon2__…'`. Workaround either way: a typed local.

- A second `` `*` `` overload on the same receiver type is invisible to importing modules: the C backend emits a raw `*` on two structs. In the defining module both overloads resolve. Workaround: one `` `*` `` per receiver (`Vec3 * Mat4`); scaling is `scaled()`.
- **A float literal in arithmetic with a `float32` widens the expression to `float64`**, and whether that is an error depends only on the position. Measured 2026-09-20 (`out/tmp/floatRepro`, card `~/metascript/.inbox/compiler/2026-09-20-float32-literal-widens.md`): `return a * 0.5;` from a `float32` function is `Return type mismatch … expected float32, got float64`; `{ a: a * 0.5 }` for a `float32` field is `Type 'float64' is not assignable to type 'float32' for field 'a'`; and `const doubled: float32 = a * 0.5;` builds and prints the right value, because the annotation coerces. Workaround: a `float32` local for the constant, which `camera.ms`, `bounds.ms` (`boundingSphereRadius`) and `meshData.ms` (`addBox`) each carry.

- **A nested object-literal key inside `Result.ok({…})` makes the std function of that name reachable.** Hit while writing M11 (card `~/metascript/.inbox/compiler/2026-09-23-literal-key-reaches-std-function.md`, repro `out/tmp/mathTime/repro.ms`): `Result.ok({ random: { state: 3 } })` for `struct E { random: S; }` emits the body of std's `Math.random`, which calls `time()` through an `extern … from "time"` with no prototype, and clang refuses it (`call to undeclared function 'time'`). The same field named `round` emits `Math.round`'s body, which happens to compile; named `other`, the math module is not compiled at all. `particles.ms` names the emitter's random state `sequence`.

- **Method-call syntax on a free function whose receiver is a `Ref` passes the checker and breaks in codegen.** Hit while writing M8 (card `~/metascript/.inbox/compiler/2026-09-22-method-call-free-function-ref-receiver.md`, repros `out/tmp/toplevelConcat/mini/repro9*`): `v.pick("k")` where `pick(v, key)` is a free function and `v: JsonValue` (a `Ref`) emits a call to an undefined `dollartmp_` helper that clang rejects; in the glTF-shaped file the same syntax produced five `internal: unresolved type (kind=48) reached codegen … proc <toplevel>` with no location. An `int32` receiver gets the correct "no member" diagnostic, so only the `Ref` path is broken. Workaround, carried through `gltf.ms`: call free functions in free-call form and bind call results to locals before any extension method — `.length` on a `JsonValue` also resolves into the struct rather than the std extension, so `gltf.ms` has its own `countOf`.

- **A `ref`-receiver free function is not an extension and does not arrive with the module import.** `function addPoint(ref b: Bounds, p: Vec3)` is `Undefined variable` in a file that imported only `Bounds`, while `isEmpty(this b: Bounds)` in the same module resolves with no import of its own (`autoPropagateModuleExtensions` registers exported *extensions*). So the mutating half of a value-struct API has to be imported by name — and it then competes in the ordinary overload set: Heaps' `Bounds.add` could not keep its name here, because std's `Set.add` / `HashSet.add` are already in it and the call reports `No matching overload for 'add'` listing only those. It is `addBounds` (measured 2026-09-20).
- **`span[0]` into a header-imported pointer parameter passes a copy (wrong code, no diagnostic).** `import { f } from "x.h"` maps `const float *` to `Borrow<float32>`; called as `f(s[0], s.length as int64)` with `s: Span<float32>`, the C is `float tmp = …; f(&tmp, len)`, so C reads one real element and then garbage (a sum over `[1, 2, 3, 4]` returns `-1.8e38`). The same call on a `Vec` (`v[0]`) is correct. On the GPU it crashed inside the driver. Workaround: declare array-taking functions as `extern function f(data: Span<float32>)`, which lowers to the header's `(const float *, int64_t)` pair (`gpu3d.ms`).
- **The same header imported from two directories compiles its `.c` twice.** `lib/m.ms` imports `./x.h`, `app/main.ms` imports `../lib/m` and `../lib/x.h`: link fails with `duplicate symbol` because the second path is not normalized (`src/test/../void3d/gpu3d.c`). Workaround: only `src/void3d` imports `gpu3d.h`; tests reach its values through the `.ms` modules.
- **`==` on a struct over 24 bytes compiles on 0.2.55 (re-checked):** a seven-`int32` struct compares and prints `true`. On 0.2.53 it failed C compile, because the generated `TEq` took values and the call site passed pointers. `pipelineCheck.ms` compares `RenderState` with `==` again.
- Header import sees functions and `static const` values only: `#define` and `enum` constants are `Undefined variable`, and `export { X } from "./x.h"` is rejected. That is why `gpu3d.h` spells its layouts as `static const int32_t`.
- **Extension methods come with any import from their module; do not import them by name.** `collectImport` registers every exported extension of the source module (`autoPropagateModuleExtensions`), so `import { RenderState } from "./pass"` is enough for `state.bits()`, `RenderState.defaults()` and `state.toString()`. Importing one by name adds a module-scope symbol of that name, and if the module also defines an extension with the same name (`import { A, toString } from "./a"` plus its own `toString(this c: C)`), the two merge into one broken overload set with no diagnostic: importers of that module get the default JSON for `c.toString()`, or an undefined-symbol link error. The void3d modules import types, constants and free functions only. The same holds for a value reached through another module: `screenKey(stage).toString()` in a file that imports `renderer` but nothing from `pipelineCache` prints `{"bits":…}`; `rendererCheck.ms` imports `PipelineKey` for that.

What the tools say about the entries above (measured 2026-09-20): the Borrow copy, the struct `==`, the double `.c` compile and a same-name extension clash all give **no** checker or LSP diagnostic. The `==` fails in clang on the generated C (mangled names, no `.ms` line), the double compile in `lld-link` (`duplicate symbol`), the clash as either a wrong result or an undefined-symbol link error; the only hint for the clash is an `'toString' is imported but never used` warning at the importer, and LSP hover/definition returning `null` on the call. Importing an extension by name when nothing clashes gives no message at all.

- **`msc lsp` on Windows answers one message late.** `msStdinHasData` (`runtime/io/streams.h`) uses `WaitForSingleObject` on the stdin handle, which is always signalled for a pipe, so the drain loop blocks in `fgets` on the next message before handling the current one; `initialize` alone gets no reply. Sending a batch and closing stdin makes it process everything (`out/tmp/diag/lspBatch.py` does that).
- **`msc check` does not resolve relative imports** (`Cannot resolve module './s'`, from any working directory, with a relative or absolute entry path), so it reports errors on files that build and test clean. Use `msc build` / `msc test` to type-check.
- **`msc build` does not rebuild when only a header that a compiled `.c` includes changed.** `main.ms` with `@compile("./value.c")`, `value.c` including `value.h` (`#define VALUE 1`), `extern function readValue(): int32`: build and run print `1`; change `value.h` to `2`, and `msc build` answers `Up to date` and the binary still prints `1` (repro in `out/tmp/cacheRepro`). Here that is every shader edit: `scripts/regen-shaders.sh` rewrites `shader3d.glsl.h`, `gpu3d.c` does not change, and the old shader stays in the binary. Workaround: after regenerating shaders, `rm out/debug/<entry>.exe out/debug/.cache/*gpu3d*` before building; after a sokol pin bump also the objects in `~/.metascript/cache/objects` built from this checkout (`setup.sh` explains).
- msc 0.2.55 rejects two things 0.2.53 accepted, both rightly: `.value` on an unnarrowed `Result`, and a float literal in a `float32` match arm (the float-literal card has the sighting). It also broke every `--os=android --app=lib` build until recompiler `3a1a2e6e`, which splits `--cc` into the executable and its arguments.
- `Math.min` / `Math.max` on two `int32` return `int32` on 0.2.55 (re-checked); on 0.2.53 they returned `float64`. The `as int32` casts in void3d are harmless and stay until their lines are touched.
- A function cannot return a `Span`, still on 0.2.55 (re-checked: `cannot return Span<int32>: a Span borrows memory owned by its source`), though CODE-STYLE lists it as measured. `passList.ms` draws its own entries (`drawPassList`) instead of handing out a `Span<int32>` of them.
- An `extern function` gets no C prototype from msc: the call compiles only if an imported header (or `@include`) declares it. On the Android clang an extern inside `when (android)` with no header was `call to undeclared function` (`-Wimplicit-function-declaration` is an error there). `gpu3d.c` wraps the Android-only `voidGpuGeneration` behind `#if defined(__ANDROID__)` instead.
